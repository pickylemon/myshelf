# ADR-012. 검색 세션 기반 상태 유지형 페이징 채택

- **상태:** 채택 (안정성 검증·보완 예정)
- **범위:** MyShelf 외부 도서 통합 검색
- **관련 문서:** [도서 검색 설계](../architecture/book-search.md), [도서 메타데이터 API 선정](../planning/book-metadata-api-selection.md)

## 배경과 문제

MyShelf는 국립중앙도서관 API를 **제목·저자·출판사별로 조회**하고, 결과를 합쳐 ISBN 기준으로 중복을 제거한다. 사용자는 검색 결과를 **20권씩 더 보기**로 확인한다.

여기에는 두 종류의 페이징이 있다.

| 구분 | 단위 | 관리 주체 |
|---|---|---|
| 외부 API | 검색 필드별 페이지, 요청 크기 100권 | MyShelf 서버 |
| 사용자 응답 | 중복 제거된 결과 최대 20권 | MyShelf 서버가 구성, 클라이언트는 더 보기 요청 |

외부 API의 한 페이지가 사용자 응답의 한 페이지에 대응하지 않는다. 예를 들어 첫 외부 조회에서 100권 이상을 확보해 20권만 반환하면, 나머지 도서는 다음 요청에 활용해야 한다. 또한 검색 조건별 결과 수가 달라 **제목은 3페이지, 출판사는 2페이지, 저자는 종료**된 상태도 가능하다.

## 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
|---|---|---|
| 클라이언트의 페이지 번호를 외부 API에 그대로 전달 | 구현 단순 | 필드별 진행 위치와 중복 제거 후 20권 구성에 맞지 않음 |
| 서버가 상태 없이 매번 앞 페이지부터 재조회 | 세션 저장 불필요 | 뒤 페이지로 갈수록 외부 호출·중복 처리 비용 반복 |
| **서버가 검색 세션 상태 유지** | 미반환 결과 재사용, 필드별 진행 위치 관리 | 세션 만료·동시성·저장소 운영 필요 |

## 결정

**검색마다 독립적인 `searchId`를 생성하는 상태 유지형 더 보기 방식**을 채택한다.

1. 최초 검색 시 Application Service가 `searchId`와 검색 상태를 생성하고, 각 검색 필드를 1페이지로 초기화한다.
2. 더 보기 요청은 `searchId`를 전달한다. Service가 상태를 조회하고 `userId`로 소유자를 검증한다.
3. 먼저 보관된 도서를 사용하고, 20권에 미달하면 아직 남은 외부 API 페이지를 조회한다.
4. 새 도서는 세션 전체 ISBN 집합과 대조한 뒤 보관하고, 이번에 반환할 최대 20권만 분리한다.
5. 다음 결과 가능성이 있으면 상태를 갱신해 저장하고, 완전히 소진되면 삭제한다.

위 흐름은 채택한 계약이다. 현재 Service는 `searchId`를 생성하고 상태 저장 키로 사용하지만, 결과·응답 DTO에는 이를 포함하지 않는다. HTTP 응답 변환도 미구현이므로 클라이언트에서 최초 검색 결과를 받아 더 보기로 이어가는 연결은 보완해야 한다. 상세 현황은 [도서 검색 설계](../architecture/book-search.md)에 기록한다.

### 유지할 검색 상태

| 필드 | 목적 |
|---|---|
| `userId` | 세션 소유자 검증 |
| `keyword` | 후속 외부 API 조회에 재사용 |
| `pendingBooks` | 조회했지만 아직 클라이언트에 반환하지 않은 도서 **전체 정보** |
| `seenIsbns` | **이미 반환한 도서와 미반환 도서 모두**를 포함한 누적 ISBN 집합 |
| `nextPageByField` | `Map<BookSearchField, Integer>`; 필드별 다음 조회 위치 |

`seenIsbns`만 저장하면 아직 반환하지 않은 도서 정보를 잃는다. `pendingBooks`만 저장하면 이전에 반환한 ISBN을 다음 외부 조회에서 다시 걸러낼 수 없다. 두 자료구조는 서로 다른 책임을 갖는다.

`nextPageByField`에서는 **조회가 끝난 필드를 제거**한다. 별도의 `exhaustedFields`나 `null` 값을 유지하지 않는다. Map이 비어 있으면 모든 외부 검색 필드가 소진된 것이다.

### `hasNext` 정책

```java
boolean hasNext = !remainingBooks.isEmpty() || !nextPageByField.isEmpty();
```

- 보관한 도서가 있으면 `true`다.
- 보관한 도서가 없어도 미조회 외부 페이지가 있으면 `true`다.
- 남은 외부 페이지가 **모두 중복 ISBN일 수 있으므로**, 더 보기에서 빈 결과가 나오는 오탐은 허용한다.
- 반대로 미반환 도서나 조회 가능한 외부 페이지가 남아 있는데 `false`를 반환하지 않도록 설계한다.

이를 확정적인 '다음 결과 존재'가 아니라 **'추가 결과 가능성'**으로 취급한다. 단순히 `hasNext`를 정확하게 만들기 위해 불필요한 외부 선조회는 하지 않는다.

## 책임 분리와 저장소 선택

- `ExternalBookSearchService`: 검색 세션 생성·진행, 사용자 응답 구성, 상태 갱신
- `ExternalBookSearchPort`: 전달받은 필드별 페이지의 외부 도서 조회 (최초/더 보기 구분 불필요)
- `BookSearchStatePort`: 상태의 저장·조회·삭제

우선 `InMemoryBookSearchStateStore`로 구현한다. 이후 동일 Port를 구현하는 Redis 저장소로 교체할 계획이다. **Redis 도입은 현재 단일 인스턴스의 필수조건이 아니라**, TTL 관리와 다중 인스턴스 상태 공유를 검토하기 위한 후속 단계다.

사용자별 등록 서재 정보는 검색 세션에 캐싱하지 않고, **이번에 반환하는 도서에 대해서만 DB에서 조회**한다. 현재 조회 결과는 ISBN별 서재 ID·이름 목록이며 독서 상태는 포함하지 않는다. 서재 연결이 없는 `UserBook`의 등록 여부도 이 조회만으로 구분하지 않는다.

## 수용한 비용과 후속 검증

- [ ] 검색 결과·응답 DTO의 `searchId` 전달과 HTTP 응답 변환 구현
- [ ] 세션 TTL 및 만료 시 응답 정책
- [ ] 동일 `searchId`의 동시 더 보기 요청에 대한 원자성 보장
- [ ] 한 HTTP 요청에서 반복되는 외부 API 호출의 횟수·시간 상한
- [ ] 외부 API 오류·빈 응답·중복 페이지 처리
- [ ] Redis 저장·복원·만료 통합 테스트

**현재 결정은 페이징 정책에 관한 것이다.** 위 안정성 항목이 모두 구현되거나 검증됐다는 뜻은 아니다.
