# ADR-011: 사용자별 도서 메타데이터 스냅샷 저장

- **Status:** Accepted
- **Date:** 2026-10-29
- **Related:** Feature 5 — 외부 도서 검색 및 사용자별 도서 관리
- **Planning:** [도서 메타데이터 API 선정 계획](../planning/book-metadata-api-selection.md)
- **Architecture:** [도메인 모델링 원칙](../architecture/domain-modeling-principles.md)

## 1. Context

MyShelf는 외부 API를 통해 도서를 검색하고, 사용자가 선택한 도서를 자신의 Shelf에 등록하여 관리하는 서비스이다.

Feature 5 설계 과정에서 도서 메타데이터의 저장 위치와 범위를 결정해야 했다.

주요 고민은 다음과 같다.

1. 도서정보를 공통 `Book` 엔티티로 분리할 것인가?
2. `UserBook`에 어떤 메타데이터를 저장할 것인가?
3. 외부 메타데이터 변경을 기존 사용자에게 전파할 것인가?
4. 책소개, 목차, 서평 등 상세정보까지 MyShelf가 직접 관리해야 하는가?

### 1.1. 서비스의 핵심 도메인

초기에는 정규화, 데이터 중복, JOIN 비용 등 기술적 관점에서 `Book` 분리 여부를 검토했다.

그러나 데이터 모델을 결정하기에 앞서 **MyShelf가 어떤 문제를 해결하려는 서비스인지** 정의할 필요가 있었다.

MyShelf의 핵심 가치는 도서정보 자체의 제공이 아니라 사용자의 독서 경험 관리이다.

- 개인 Shelf 구성 및 관리
- 도서를 하나 이상의 Shelf에 연결
- 사용자별 독서 상태 관리
- Shelf 내 도서 정렬
- 현재 Shelf에 등록된 도서 검색

따라서 공통 도서 카탈로그보다는 사용자와 도서의 관계를 핵심 도메인으로 판단했다.

이러한 제품적 판단을 `UserBook` 중심 데이터 모델의 주요 설계 근거로 삼았다.

제품 요구사항에서 도메인 모델과 아키텍처 설계로 이어지는 관점은 [도메인 모델링 원칙](../architecture/domain-modeling-principles.md)에 별도로 정리한다.

### 1.2. 공통 Book 엔티티 도입의 장단점

일반적인 정규화 관점에서는 도서의 고유 정보와 사용자별 관리 정보를 분리할 수 있다.

```text
Book
 ├── isbn
 ├── title
 ├── author
 ├── publisher
 └── coverImageUrl
       ↑
    UserBook
     ├── userId
     ├── bookId
     └── readingStatus
```

공통 `Book`을 사용하면 동일 ISBN의 메타데이터를 여러 사용자 사이에서 공유할 수 있다.

그러나 공통 데이터를 갱신하면 이를 참조하는 사용자에게도 변경이 반영된다.

예를 들어 다음 상황을 가정한다.

1. 사용자 A가 특정 ISBN의 도서를 등록한다.
2. 이후 외부 제공자가 도서 제목이나 표지 정보를 수정한다.
3. 사용자 B가 동일 ISBN을 등록하는 과정에서 공통 `Book`의 정보를 갱신한다.
4. 사용자 A가 조회하는 도서정보도 변경된다.

A의 `UserBook` 레코드가 직접 수정된 것은 아니지만, 공통 `Book`의 변경으로 A에게 표시되는 정보가 달라진다.

이러한 변경 전파는 도서정보의 최신성과 일관성이 중요한 서비스에서는 장점이 될 수 있다.

하지만 MyShelf에는 이미 등록한 도서의 메타데이터를 외부 변경에 따라 자동 갱신해야 한다는 요구사항이 없다.

오히려 사용자별로 등록한 도서정보를 독립적으로 유지하는 편이 현재 서비스 성격에 적합하다.

### 1.3. UserBook의 데이터 보존 성격

MyShelf에서는 `UserBook`이 Shelf 연결과 독립적으로 존재한다.

- 하나의 `UserBook`은 여러 Shelf에 연결될 수 있다.
- 모든 Shelf에서 제거되어도 `UserBook`은 유지한다.
- 독서 상태는 `UserBook`에 속하며 모든 Shelf에서 공유된다.

따라서 `UserBook`은 사용자가 등록한 도서에 대한 지속적인 관리 기록의 성격을 갖는다.

다만 과거의 모든 변경을 보존하는 감사 로그나 불변 이력 테이블은 아니다.

이러한 특성을 고려하여 도서의 최소 메타데이터를 **최초 등록 시점의 스냅샷**으로 저장하는 방식을 선택했다.

## 2. Decision

### 2.1. 공통 Book 엔티티를 도입하지 않는다

별도의 공통 `Book` 엔티티 및 `books` 테이블은 생성하지 않는다.

사용자별 `UserBook`에 등록 당시의 최소 도서 메타데이터를 저장한다.

```text
UserBook
 ├── id
 ├── userId
 ├── isbn
 ├── title
 ├── author
 ├── publisher
 ├── coverImageUrl
 └── readingStatus

ShelfBook
 ├── shelfId
 ├── userBookId
 └── sortOrder
```

위 구조는 주요 도메인 속성을 표현한 것이다. 실제 FK, 상태 코드, 생성·수정 시각 등은 기존 영속성 설계에 따른다.

`publisher`와 `coverImageUrl`은 이번 결정에 따라 추가할 저장 대상이며, 필요한 Flyway 마이그레이션과 엔티티 변경을 구현 단계에서 반영한다.

### 2.2. UserBook에는 최소 메타데이터만 저장한다

| 필드 | 목적 | 필수 여부 |
|---|---|---|
| `isbn` | 도서 식별 및 중복 등록 방지 | 필수 |
| `title` | 도서명 표시 | 필수 |
| `author` | 저자 표시 및 도서 구분 | 누락 허용 |
| `publisher` | 출판사 표시 및 판본 구분 보조 | 누락 허용 |
| `coverImageUrl` | Shelf의 표지 이미지 표시 | 누락 허용 |

`readingStatus`는 외부 도서 메타데이터가 아니라 MyShelf가 관리하는 사용자별 정보로서 별도로 유지한다.

다음 항목은 현재 저장 대상에서 제외한다.

- 책소개, 목차, 서평
- 가격 및 판매 정보
- 페이지 수
- 출판일 및 상세 판본 정보
- 시리즈 정보
- 기타 서지 분류 정보

외부 API 응답에 해당 필드가 존재하더라도 현재 기능에서 사용하지 않는다면 매핑하거나 저장하지 않는다.

향후 구체적인 기능 요구사항이 생기면 필요한 메타데이터를 추가할 수 있다.

### 2.3. 등록 시점의 메타데이터를 스냅샷으로 보존한다

사용자가 도서를 최초 등록할 때 외부 API에서 조회한 최소 메타데이터를 `UserBook`에 저장한다.

동일 사용자가 같은 ISBN을 다른 Shelf에 다시 등록하는 경우 기존 `UserBook`을 재사용한다.

이때 외부 API가 새로운 제목이나 표지 URL을 반환하더라도 기존 메타데이터를 자동 갱신하지 않는다.

```text
사용자 A
 └── UserBook
      ├── ISBN: 978...
      ├── 제목: A의 최초 등록 당시 값
      └── 표지: A의 최초 등록 당시 URL

사용자 B
 └── UserBook
      ├── ISBN: 978...
      ├── 제목: B의 최초 등록 당시 값
      └── 표지: B의 최초 등록 당시 URL
```

동일 ISBN이더라도 사용자별로 서로 다른 시점의 메타데이터를 보유할 수 있다.

이는 공통 메타데이터의 최신성보다 **사용자별 등록 정보의 독립성**을 우선한 의도적인 정책이다.

단, 스냅샷은 DB에 저장한 값에 대한 정책이다. 표지 이미지 URL이 가리키는 외부 콘텐츠의 변경이나 접근 불가까지 방지하는 것은 아니다.

### 2.4. 사용자 관리 정보는 별도로 변경할 수 있다

메타데이터 자동 갱신 방지 정책은 독서 상태 변경을 제한하지 않는다.

`readingStatus`는 사용자 요청에 따라 변경할 수 있으며, 변경 내용은 해당 `UserBook`이 연결된 모든 Shelf에 반영된다.

도서 등록의 세부 정책은 [Feature 5의 중복 등록 처리](../planning/feature-5-book-management.md#35-동일-shelf의-중복-등록-처리)와 [독서 상태·재등록 처리](../planning/feature-5-book-management.md#36-등록-시-독서-상태와-재등록-처리)를 기준으로 한다.

2026-11-03 문서 정리에서 확정 기획과 달랐던 중복 등록 거부 표현을 서버의 등록 대상 필터링으로 정정했다. 독서 상태의 선택 입력 설명도 필수 입력 계약에 맞게 정정했다. 이 ADR은 사용자별 메타데이터 스냅샷을 유지하는 결정과 근거를 다루며, 입력·중복 처리 계약을 별도로 중복 관리하지 않는다.

Shelf에서 도서를 제거할 때는 `ShelfBook` 연결만 삭제하며 `UserBook`은 유지한다.

### 2.5. 상세 도서정보를 직접 관리하지 않는다

MyShelf는 도서 검색 및 등록에 필요한 기본 메타데이터와 사용자의 등록 상태를 제공한다.

책소개, 목차, 서평 등을 영구 저장하거나 이를 중심으로 한 도서 상세 페이지를 초기 기능에 포함하지 않는다.

상세 정보가 필요한 사용자에게는 향후 외부 도서정보 사이트 또는 서점의 상세 페이지로 이동하는 기능을 제공할 수 있다.

단, 국립중앙도서관 ISBN API의 `TITLE_URL`은 표지 이미지 URL이고 `PUBLISHER_URL`은 출판사 홈페이지 주소이므로, 서점 상품 상세 페이지 링크를 제공하는 방법은 별도로 검토한다.

### 2.6. 외부 응답 모델과 내부 모델을 분리한다

외부 API의 응답 구조가 MyShelf의 Domain 및 Application 계층으로 직접 유입되지 않도록 한다.

```text
외부 도서 API
      ↓
External Adapter DTO
      ↓
Application 내부 도서정보 모델
      ↓
사용자별 등록 정보 결합
      ↓
Web Response DTO
      ↓
MyShelf 클라이언트
```

외부 응답 DTO는 제공자의 JSON 명세에 맞추되 필요한 필드만 역직렬화한다.

Application 모델은 MyShelf의 요구사항에 맞춰 정의한다.

Web Response DTO는 사용자에게 제공할 REST 응답 형식을 표현한다.

이를 통해 외부 API 교체나 응답 명세 변경이 MyShelf 내부 모델과 Web API에 불필요하게 전파되지 않도록 한다.

### 2.7. 외부 데이터 이용 조건을 준수한다

최소 메타데이터 스냅샷을 저장하기로 결정했더라도 실제 저장과 표지 이미지 표시가 외부 제공자의 이용 조건에 부합하는지는 별도 검증이 필요하다.

특히 공공데이터의 일반적인 이용 조건과 표지 이미지 등 개별 콘텐츠의 권리 조건이 동일하다고 단정하지 않는다.

외부 API별 이용 조건을 확인한 뒤 실제 저장 및 재사용 방식을 확정한다.

해당 검증은 [도서 메타데이터 API 선정 계획](../planning/book-metadata-api-selection.md)에서 관리한다.

## 3. Alternatives Considered

### 대안 A. 공통 Book 엔티티 분리

공통 `Book`에 메타데이터를 저장하고, `UserBook`은 사용자의 도서 등록 및 독서 상태만 관리한다.

**장점**
- 동일 ISBN의 메타데이터 중복 저장 감소
- 공통 도서정보의 일관성 확보
- 도서정보 일괄 수정 및 관리에 유리

**단점**
- 공통 메타데이터 변경이 여러 사용자에게 전파될 수 있음
- 공통 정보의 생성·갱신 정책 필요
- 현재 기능 범위 대비 모델 및 관리 복잡성 증가

사용자별 등록 정보의 독립성을 우선하므로 채택하지 않는다.

### 대안 B. 공통 Book과 사용자별 스냅샷 병행

공통 `Book`을 유지하면서 사용자별 등록 당시 메타데이터도 `UserBook`에 별도로 저장한다.

**장점**
- 공통 도서정보와 등록 당시 정보를 모두 관리 가능
- 공통 메타데이터 갱신과 사용자별 스냅샷 보존을 분리 가능

**단점**
- 두 종류의 도서 메타데이터를 관리해야 함
- 조회 시 어느 정보를 우선 사용할지 정책 필요
- 저장 및 동기화 복잡성 증가

현재는 이러한 구조를 정당화할 요구사항이 없어 채택하지 않는다.

### 대안 C. UserBook에 ISBN만 저장하고 매번 외부 조회

`UserBook`에는 ISBN과 독서 상태 등 사용자별 정보만 저장하고, 제목·저자·표지는 조회할 때마다 외부 API에서 가져온다.

**장점**
- 도서 메타데이터의 중복 저장 최소화
- 별도 메타데이터 관리 부담 감소

**단점**
- Shelf 조회가 외부 API의 가용성과 응답 시간에 의존
- 외부 API 장애 시 기존 도서의 표시 정보가 누락될 수 있음
- API 호출량 증가
- 외부 메타데이터 변경이 조회 결과에 즉시 반영됨

핵심 기능인 Shelf 조회의 외부 의존성을 줄이기 위해 채택하지 않는다.

## 4. Consequences

### 4.1. 긍정적 영향

- 사용자별 등록 도서 메타데이터의 독립성 확보
- 외부 메타데이터 변경의 영향 범위 제한
- 기존 Shelf 조회 시 외부 API 호출 불필요
- 외부 API 장애 중에도 저장된 도서정보 조회 가능
- 공통 도서 카탈로그 관리 복잡성 감소
- 사용자별 Shelf 및 독서 상태 관리라는 핵심 도메인에 집중 가능

### 4.2. 부정적 영향 및 트레이드오프

- 동일 ISBN에 대한 메타데이터 중복 저장
- 동일 도서의 정보가 사용자별로 달라질 수 있음
- 잘못 저장한 메타데이터가 자동으로 수정되지 않음
- 전체 사용자 대상 메타데이터 일괄 정정이 어려움
- 외부 표지 이미지 URL의 지속적인 유효성을 보장할 수 없음

이는 현재 MyShelf의 요구사항과 규모에서 수용할 수 있는 트레이드오프로 판단한다.

### 4.3. 구현에 미치는 영향

- `Book` 엔티티 및 `books` 테이블은 추가하지 않는다.
- 기존 `UserBook`, `ShelfBook` 관계를 유지한다.
- `UserBook`에 출판사와 표지 URL을 추가한다.
- 최초 등록 시에만 메타데이터를 저장한다.
- 재등록 시 메타데이터를 자동 갱신하지 않는다.
- 등록된 도서의 조회는 MyShelf DB를 기준으로 한다.
- 외부 API DTO와 내부 데이터 모델을 분리한다.
- 실제 필드 저장은 선택한 API의 이용 조건 확인을 전제로 한다.

## 5. Reconsideration Criteria

다음 요구사항이 발생하면 공통 `Book` 엔티티 도입을 재검토한다.

- 사용자 간 공통 도서정보의 일관성이 중요해지는 경우
- ISBN별 독서 통계나 추천 기능이 추가되는 경우
- 공통 도서 카탈로그를 별도로 관리해야 하는 경우
- 메타데이터 중복으로 실질적인 저장·운영 문제가 발생하는 경우
- 전체 사용자 대상 도서정보 일괄 갱신이 필요한 경우
- 사용자별 스냅샷과 공통 최신 정보를 동시에 제공해야 하는 경우

단순히 데이터 중복이 존재한다는 이유만으로 공통 `Book`을 도입하지는 않는다.

## 6. Summary

MyShelf는 도서 메타데이터 자체보다 **사용자와 도서 사이의 관계를 관리하는 서비스**이다.

따라서 공통 `Book` 엔티티를 도입하지 않고, `UserBook`에 ISBN·제목·저자·출판사·표지 URL의 최소 메타데이터를 등록 당시의 스냅샷으로 저장한다.

이 결정은 데이터 정규화와 공통 정보 일관성의 이점을 일부 포기하는 대신, 사용자별 데이터 독립성과 외부 시스템에 대한 의존성 감소를 선택한 것이다.

상세 도서정보는 현재 관리 범위에서 제외하며, MyShelf는 Shelf 구성과 독서 상태 관리 등 핵심 기능에 집중한다.
