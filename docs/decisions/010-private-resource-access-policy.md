# ADR-010: 비공개 리소스 접근 및 삭제 응답 정책

- **Status:** Accepted
- **Date:** 2026-10-27

## 1. Context

MyShelf의 Shelf는 사용자별 비공개 리소스이며, 소유자만 조회·수정·삭제할 수 있다.

다른 사용자의 Shelf에 접근했을 때 다음 두 방식 중 어떤 응답을 반환할지 결정해야 했다.

- **403 Forbidden:** 리소스는 존재하지만 접근 권한이 없음을 알린다.
- **404 Not Found:** 리소스의 존재 여부를 노출하지 않는다.

또한 DELETE 요청에서 대상이 존재하지 않을 경우 `404`와 `204` 중 어떤 응답을 사용할지도 결정할 필요가 있었다.

## 2. Decision

### 2.1. 비공개 리소스 접근은 404로 처리

인증된 사용자의 소유권 범위에서 리소스를 조회한다.

```java
findByIdAndUserId(shelfId, userId);
```

다음 두 상황은 모두 `SHELF_NOT_FOUND(404)`로 처리한다.

- 해당 ID의 Shelf가 존재하지 않는 경우
- Shelf는 존재하지만 다른 사용자의 소유인 경우

이는 **리소스 자체의 존재 여부가 아니라, 현재 사용자가 접근할 수 있는 리소스의 존재 여부**를 기준으로 판단하는 정책이다.

### 2.2. DELETE는 대상의 존재 여부를 확인

현재 MyShelf에서는 삭제 대상이 존재해야 정상 삭제로 처리한다.

| 상황 | HTTP 응답 |
|---|---|
| 본인 Shelf 정상 삭제 | 204 No Content |
| 존재하지 않는 Shelf | 404 Not Found |
| 다른 사용자의 Shelf | 404 Not Found |
| 인증되지 않은 요청 | 401 Unauthorized |

삭제 후 같은 요청을 반복하면 `204 → 404`로 응답이 달라질 수 있다.

그러나 서버에 남는 의도된 최종 상태는 동일하므로 **DELETE의 멱등성을 위반하지 않는다.**

## 3. Rationale

### 리소스 존재 여부 보호

403을 반환하면 요청자가 타인의 비공개 Shelf가 존재한다는 사실을 추측할 수 있다.

404로 통일하면 존재하지 않는 Shelf와 접근할 수 없는 Shelf를 응답만으로 구분하기 어렵다.

RFC 9110에서도 접근이 금지된 리소스의 존재를 숨기기 위해 404를 반환하는 것을 허용한다.

### API 응답의 일관성

조회·수정·삭제 모두 동일한 소유권 조회 조건과 `SHELF_NOT_FOUND` 정책을 적용한다.

### DELETE의 명확한 결과 표현

대상이 없어도 204를 반환하는 방식도 가능하지만, 현재는 삭제 대상이 존재하지 않는 상황을 명시적으로 알리는 404를 선택했다.

이는 CRUD 동작의 결과를 이해하고 검증하기 쉽게 하기 위한 결정이다.

## 4. Consequences

**장점**
- 타인의 비공개 리소스 존재 여부 노출을 줄인다.
- 소유권 검증을 데이터 조회 조건에 포함할 수 있다.
- 조회·수정·삭제의 예외 처리 정책이 일관된다.

**트레이드오프**
- 클라이언트는 리소스가 실제로 없는지, 접근 권한이 없는지 구분할 수 없다.
- DELETE 재요청 시 404를 받을 수 있으므로 클라이언트가 이를 고려해야 한다.

## 5. 향후 고려사항

403을 사용하지 않겠다는 결정은 아니다.

향후 서재 공유 기능이 도입되어 사용자가 특정 Shelf의 **읽기 권한은 있지만 수정 권한은 없는 경우**, 403 Forbidden이 적절할 수 있다.

또한 삭제 요청의 재시도가 중요한 API에서는 존재하지 않는 리소스에도 204를 반환하는 정책을 재검토할 수 있다.

현재 결정은 **사용자별 비공개 Shelf의 소유권 모델**을 기준으로 한다.
