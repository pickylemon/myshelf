# Schema Decisions

MyShelf 데이터베이스 설계 과정에서 결정한 주요 사항과 선택 근거를 기록한다.

실제 테이블 구조는 [Flyway SQL](../../src/main/resources/db/migration), 현재 컬럼·관계는 [ERD 설명](erd.md)을 기준으로 확인한다. 이 문서는 스키마 선택의 이유와 제약을 요약하며, 개별 비즈니스 정책이나 전체 마이그레이션 목록을 중복 관리하지 않는다.

## 1. 별도의 Books 테이블을 두지 않는다

**결정:** `books`를 제거하고 `user_books`에 필요한 도서정보를 저장한다.

**근거:**
- 외부 도서 API가 도서정보의 원본 역할을 한다.
- 현재는 서비스 전체가 공유하는 도서 마스터 데이터를 관리할 필요가 없다.
- 사용자별 독서 상태와 도서 등록 이력을 UserBook에서 관리한다.
- Shelf 표시를 위해 최소한의 도서정보를 저장한다.

**트레이드오프:** 동일 ISBN의 도서정보가 사용자별로 중복 저장될 수 있다. 현재 규모에서는 이를 허용한다. 공통 Book과 사용자별 스냅샷을 비교한 상세 근거는 [ADR-011](../decisions/011-user-book-metadata-snapshot.md)에 보존한다.

## 2. ISBN을 사용자별 도서 식별 기준으로 사용한다

**결정:** `UNIQUE(user_id, isbn)`을 적용하고 ISBN을 필수값으로 관리한다.

**근거:**
- 동일 사용자의 동일 ISBN 중복 등록을 방지한다.
- 같은 작품이라도 ISBN이 다른 판본은 별개 도서로 허용한다.
- 초기에는 외부 API에서 조회된 ISBN이 있는 책만 등록한다.

입력 검증·재사용 등 현재 ISBN 계약은 [현행 도서 관리 정책](../planning/book-management-policy.md#1-등록과-도서-식별)을 따른다. 메타데이터 확보 순서는 도서 관리 아키텍처에서 확인한다.

## 3. UserBook과 ShelfBook의 생명주기를 분리한다

**결정:** Shelf에서 도서를 제거할 때 ShelfBook만 삭제하고 UserBook은 보존한다.

**근거:**
- UserBook은 사용자의 도서 등록 이력과 독서 상태를 관리한다.
- 하나의 UserBook이 여러 Shelf에 존재할 수 있다.
- 마지막 Shelf에서 제거하더라도 향후 필사 등 관련 기록을 유지해야 한다.

별도의 Soft Delete는 도입하지 않는다.

수명·재등록의 상세 계약은 [현행 도서 관리 정책](../planning/book-management-policy.md)을 따른다. 소프트 삭제 없이 연결을 기준으로 판단한 원리는 [학습 기록](../learning/database/soft-delete-and-source-of-truth.md), 현재 컬럼과 마이그레이션별 반영은 ERD 설명에서 관리한다.

## 4. 독서 상태는 Lookup Table로 관리한다

**결정:** `reading_statuses` 테이블을 생성하고 상태 코드를 PK로 사용한다.

초기 상태:
- `WANT_TO_READ`
- `READING`
- `READ`

**근거:**
- DB에서 허용된 상태를 기준 데이터로 명시적으로 관리한다.
- FK를 통해 유효하지 않은 상태 저장을 방지한다.
- 상태 코드를 PK로 사용하여 Java Enum과의 숫자 ID 매핑을 피한다.

Flyway가 기준 데이터를 등록하고, Java Enum과의 일치 여부는 애플리케이션 변경 시 관리한다.

## 5. Shelf와 UserBook의 소유권 일치는 애플리케이션에서 검증한다

**결정:** 별도의 복합 FK를 추가하지 않고, 애플리케이션에서 인증된 사용자 기준으로 소유권을 확인한다.

**근거:**
- Shelf와 UserBook은 각각 사용자 소유 데이터를 나타낸다.
- 현재 FK는 참조 대상의 존재만 보장하며 소유자 일치까지 보장하지 않는다.
- 연결 생성 UseCase에서 양쪽 소유권을 검증하는 방식이 현재 규모에 적절하다.

**트레이드오프:** DB 자체는 서로 다른 사용자의 데이터 연결을 차단하지 못한다. 따라서 관련 생성 경로와 테스트에서 규칙을 보장해야 한다.

## 6. 인덱스는 조회 방향을 고려하여 구성한다

**결정:** PK와 UNIQUE 인덱스 외에 다음 일반 인덱스를 사용한다.

- `idx_shelf_books_user_book_id`: UserBook 기준 소속 Shelf 탐색

Shelf의 `idx_shelves_user_id`는 V2에서 제거했다. `uk_shelves_name_per_user(user_id, name)`의 복합 인덱스로 사용자별 조회를 지원한다.

**근거:**
- PostgreSQL은 FK 컬럼에 인덱스를 자동 생성하지 않는다.
- `UNIQUE(shelf_id, user_book_id)`는 Shelf 기준 탐색에 활용할 수 있다.
- `user_book_id`만으로 역방향 탐색하는 경우를 위해 별도 인덱스를 둔다.
- `UNIQUE(user_id, isbn)`는 사용자별 도서 탐색에도 활용할 수 있으므로 `user_books(user_id)` 단독 인덱스는 추가하지 않는다.

일반 인덱스의 실제 효과는 향후 조회 패턴 및 실행 계획으로 검증한다.

## 7. 초기 개발 단계에서 Flyway V1을 재작성한다

**결정:** 기존 데이터를 보존할 필요가 없는 초기 개발 단계에서는 V2 데이터 이전 마이그레이션 대신 V1을 재작성한다.

**근거:**
- 기존 DB는 초기 개발 데이터만 존재한다.
- 데이터 이전 SQL을 유지할 실질적 필요가 없다.
- 최종 초기 스키마를 단순하게 구성할 수 있다.

**조건:** 기존 개발 DB를 초기화하고 새로운 V1을 적용한다.

이후 스키마 변경은 새로운 Flyway 버전으로 관리한다.

## 8. 추후 결정 사항

다음 사항은 해당 기능 구현 시 결정한다.

- Shelf 내부 배치 순서(`position`)의 갱신 및 제약조건
- ISBN 정규화 도입 필요성 (현재 적용하지 않음)
- 추가 조회 인덱스의 필요성

---

이 문서는 설계 선택의 이유를 남기기 위한 기록이며, 실제 DB 구조의 기준은 Flyway 마이그레이션이다.
