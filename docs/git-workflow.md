# MyShelf — Git 작업 규칙

MyShelf는 **GitHub Flow 기반**으로 브랜치와 PR을 관리한다. 변경 이력과 CI 검증을 유지하되, 개인 학습 프로젝트에 불필요한 절차는 최소화한다.

>MyShelf는 개인 학습 프로젝트로, 현재 별도의 릴리스 브랜치나 병렬 버전 관리가 필요하지 않다. 따라서 main 중심의 단순한 GitHub Flow를 채택한다. 단기 작업 브랜치와 PR 기반 CI 검증을 통해 변경 이력을 관리하며, 향후 협업 및 릴리스 관리 요구가 복잡해지면 브랜치 전략을 재검토한다.

## 1. 브랜치 전략

- `main`은 보호 브랜치로 유지하며, 변경사항은 PR을 통해 병합한다.
- 작업별 단기 브랜치를 생성하고, 병합 후 삭제한다. 기존 작업 브랜치는 원칙적으로 재사용하지 않는다.
- `develop`, `release` 등의 장기 브랜치는 현재 운영하지 않는다.
- 브랜치는 파일별이 아닌 **논리적인 작업 단위**로 생성한다.

브랜치 이름은 변경 목적에 따라 `feature/`, `fix/`, `docs/`, `test/`, `ci/`, `infra/`, `chore/` 등을 사용한다.

## 2. 커밋과 PR

- 커밋 메시지는 기존 Conventional Commits 형식을 따른다.
- 하나의 커밋은 가능한 한 하나의 논리적인 변경 목적을 담는다.
- PR은 변경 목적과 주요 내용, 검증 결과를 명확히 기록한다.
- PR 생성 후에도 수정 커밋을 추가할 수 있으며, 충분히 검토한 후 병합한다.
- 필수 CI 통과 후 병합하며, 보호 규칙을 임의로 우회하지 않는다.

## 3. 브랜치 관리

- 작업 브랜치는 최신 `main`을 기준으로 생성한다.
- 작업 중에는 필요에 따라 `main`의 변경사항을 반영한다.
- 병합 후 로컬 `main`을 갱신하고 완료된 브랜치를 정리한다.
- 공유된 커밋의 이력을 임의로 재작성하지 않는다.
- Git 명령을 실행하기 전 현재 브랜치와 변경 상태를 확인한다.

## 4. 운영 원칙

- 단순 문서 수정에도 `main` 보호 규칙은 적용한다.
- 모든 변경에 별도의 Issue나 ADR을 요구하지 않는다.
- 프로젝트 규모와 협업·배포 요구가 달라지면 전략을 재검토한다.
- AI의 Git 명령 실행 권한은 루트 `AGENTS.md`를 따른다.

**브랜치는 작업 공간, 커밋은 변경 기록, PR은 변경 목적과 검증 이력을 관리하는 단위다.**
