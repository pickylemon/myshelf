# 통합 테스트 설계와 테스트 픽스처 구성

## 1. 학습 배경

MyShelf의 `ShelfReadIntegrationTest`를 검토하면서 테스트 코드가 실제 애플리케이션의 실행 흐름과 다르게 구성된다는 점을 발견했다.

예를 들어 하나의 테스트 메서드 안에서 다음 작업들이 함께 수행된다.

```java
UUID userId = createUser();
Shelf shelf = createShelf(userId, "내 서재", "설명");

mockMvc.perform(
    get("/shelves/{shelfId}", shelf.getId())
        .header(HttpHeaders.AUTHORIZATION, bearerToken(userId))
);

jdbcTemplate.queryForMap(...);
```

실제 애플리케이션에서는 사용자 생성, Shelf 저장, HTTP 요청, DB 직접 조회가 이런 형태로 한곳에서 실행되지 않는다.

그런데 테스트에서는 서로 다른 계층의 코드를 조합해 사용한다.

이를 통해 **테스트는 운영 코드의 실행 순서를 그대로 복제하는 것이 아니라, 검증에 필요한 상황을 구성하고 특정 동작의 결과를 확인하는 작업**이라는 점을 이해했다.

## 2. 테스트의 기본 구조: Given–When–Then

테스트는 크게 세 단계로 생각할 수 있다.

### Given — 어떤 상황인가?

테스트를 수행하기 위한 사전 조건을 구성한다.

예를 들어 "다른 사용자의 Shelf는 조회할 수 없다"는 규칙을 검증하려면 다음 데이터가 필요하다.

- 사용자 A
- 사용자 B
- 사용자 B가 소유한 Shelf
- 사용자 A의 JWT

이 데이터들은 테스트를 위한 준비물이며, **테스트 픽스처(Test Fixture)**라고 한다.

### When — 어떤 행동을 수행하는가?

검증하려는 실제 기능을 실행한다.

```java
mockMvc.perform(
    get("/shelves/{shelfId}", otherShelfId)
        .header(HttpHeaders.AUTHORIZATION, bearerToken(userA))
);
```

이 테스트에서는 사용자 A가 사용자 B의 Shelf를 조회하는 것이 핵심 행동이다.

### Then — 어떤 결과가 나와야 하는가?

실행 결과가 요구사항과 일치하는지 확인한다.

```java
.andExpect(status().isNotFound())
.andExpect(jsonPath("$.code").value("SHELF_NOT_FOUND"));
```

MyShelf에서는 다른 사용자의 Shelf와 존재하지 않는 Shelf를 모두 404로 처리하는 정책을 사용한다.

따라서 이 테스트는 사용자별 데이터 격리 정책이 정상적으로 적용되는지 검증한다.

## 3. 테스트 데이터를 준비할 때 실제 API를 모두 호출해야 할까?

반드시 그럴 필요는 없다.

`ShelfReadIntegrationTest`에서는 사용자와 Shelf를 준비하기 위해 Persistence Adapter를 직접 사용한다.

```java
private UUID createUser() {
    UUID userId = UUID.randomUUID();

    userPersistenceAdapter.save(
        new User(
            userId,
            "test-" + userId + "@example.com",
            "encoded-password"
        )
    );

    return userId;
}
```

```java
private Shelf createShelf(
        UUID userId,
        String name,
        String description
) {
    return shelfPersistenceAdapter.save(
        new Shelf(
            UUID.randomUUID(),
            name,
            description,
            userId
        )
    );
}
```

이렇게 하면 회원가입 API와 Shelf 생성 API를 호출하지 않아도 테스트에 필요한 데이터를 준비할 수 있다.

### 왜 이렇게 하는가?

검증하려는 기능이 Shelf 조회이기 때문이다.

만약 조회 테스트를 위해 매번 다음 API를 호출한다면 어떻게 될까?

```text
회원가입 API
    ↓
로그인 API
    ↓
Shelf 생성 API
    ↓
Shelf 조회 API
    ↓
응답 검증
```

조회 기능과 무관한 API에 대한 의존성이 커진다.

예를 들어 Shelf 생성 API에 문제가 발생하면 조회 기능 자체는 정상이어도 조회 테스트가 실패할 수 있다.

따라서 조회 기능을 검증할 때는 필요한 데이터를 직접 준비하고, **검증 대상인 Shelf 조회 API만 실제 요청 흐름으로 실행하는 방식**을 사용할 수 있다.

물론 회원가입부터 Shelf 조회까지의 전체 사용자 흐름을 검증하려는 테스트라면 여러 API를 순서대로 호출하는 것도 적절하다.

핵심은 테스트 목적에 따라 실행 범위를 선택하는 것이다.

## 4. 테스트 코드에 서로 다른 계층이 함께 등장해도 될까?

가능하다.

특히 통합 테스트에서는 테스트 준비, 실행, 검증에 서로 다른 도구를 사용할 수 있다.

| 테스트 코드 | 역할 |
|---|---|
| `UserPersistenceAdapter.save()` | 사용자 데이터 준비 |
| `ShelfPersistenceAdapter.save()` | Shelf 데이터 준비 |
| `AccessTokenIssuerPort.issue()` | 인증 토큰 준비 |
| `MockMvc.perform()` | 검증 대상 API 실행 |
| `andExpect()` | HTTP 결과 검증 |
| `JdbcTemplate` | 실제 DB 상태 검증 |
| `@AfterEach` | 테스트 데이터 정리 |

이것이 헥사고날 아키텍처의 계층 분리를 위반하는 것은 아니다.

실제 운영 코드에서는 Controller가 Persistence Adapter를 직접 호출하지 않도록 설계하지만, **테스트 코드는 애플리케이션의 비즈니스 계층이 아니라 검증을 위한 코드**이기 때문이다.

다만 테스트 준비 과정이 검증 대상의 동작을 대신 수행해서는 안 된다.

예를 들어 Shelf 생성 API를 검증하면서 Adapter로 Shelf를 직접 저장해 놓고 존재 여부만 확인한다면, 생성 API가 실제로 정상 동작하는지 증명할 수 없다.

테스트 데이터 준비와 검증 대상 실행을 명확히 구분해야 한다.

## 5. 좋은 테스트 시나리오는 어떻게 생각할까?

테스트 작성에서 어려운 부분은 Mockito나 JUnit 문법만이 아니다.

**어떤 상황을 만들어야 비즈니스 규칙이 올바르게 검증되는지 생각하는 것**이 중요하다.

처음부터 가능한 모든 경우를 나열하기보다 다음 순서로 접근한다.

### 5.1 정상적인 상황

기능이 의도대로 동작하는 가장 기본적인 상황이다.

예를 들어 Shelf 상세 조회라면:

- 내가 소유한 Shelf가 존재한다.
- 정상적인 JWT를 전달한다.
- HTTP 200과 올바른 Shelf 정보가 반환된다.

### 5.2 데이터가 없는 상황

대상이 존재하지 않을 때 어떻게 동작해야 하는지 검증한다.

- Shelf 목록이 비어 있다.
- 존재하지 않는 Shelf ID를 조회한다.

목록 조회는 200과 빈 배열을 반환하고, 단건 조회는 404를 반환하도록 정책을 정했다.

### 5.3 권한이 없는 상황

사용자별 접근 통제가 중요한 서비스라면 반드시 고려해야 한다.

- 사용자 A가 B의 Shelf를 조회한다.
- 사용자 A가 B의 Shelf를 수정한다.
- 사용자 A가 B의 Shelf를 삭제한다.
- 인증 없이 요청한다.

여기서 인증 실패와 소유권 조건에 맞는 리소스가 없는 상황은 구분한다.

### 5.4 경계 조건

유효성 검증이나 DB 제약조건의 경계값을 확인한다.

예를 들어 Shelf 이름의 최대 길이가 255자라면:

- 255자 이름은 허용되는가?
- 256자 이름은 거부되는가?
- `null`, 빈 문자열, 공백만 있는 문자열은 어떻게 처리하는가?

중요한 것은 경계값을 많이 만드는 것이 아니라 실제 요구사항과 제약조건에서 의미 있는 값을 선택하는 것이다.

### 5.5 실패 이후 데이터 상태

쓰기 작업에서는 예외 응답뿐 아니라 DB 데이터가 의도치 않게 변경되지 않았는지도 확인해야 한다.

예를 들어 중복된 Shelf 이름으로 수정을 요청했다면:

- HTTP 409가 반환되는가?
- 기존 이름과 설명이 그대로 유지되는가?
- 다른 사용자의 Shelf에 영향이 없는가?

이런 테스트는 응답 코드만 확인하는 것보다 데이터 정합성을 더 강하게 검증할 수 있다.

## 6. 테스트 결과는 무엇을 확인해야 할까?

테스트의 목적에 따라 검증 수준을 정한다.

### 단순 응답 검증

```java
.andExpect(status().isOk());
```

이 검증은 HTTP 요청이 성공했다는 사실을 확인한다.

하지만 올바른 데이터를 반환했는지는 알 수 없다.

### 응답 내용 검증

```java
.andExpect(jsonPath("$.id").value(shelfId.toString()))
.andExpect(jsonPath("$.name").value("내 서재"));
```

정확한 데이터를 반환하는지 확인한다.

### 실제 DB 상태 검증

```java
Map<String, Object> stored =
    jdbcTemplate.queryForMap(
        "select name, description from shelves where id = ?",
        shelfId
    );
```

DB에 저장된 결과를 직접 확인한다.

특히 생성·수정·삭제 테스트에서는 HTTP 응답과 실제 DB 상태를 함께 확인하는 것이 유용하다.

반면 단순 조회 테스트에서 모든 데이터를 매번 DB로 재조회할 필요는 없다. 사전 데이터가 명확하다면 기대한 응답을 직접 검증하는 것으로 충분할 수 있다.

**검증이 많다고 반드시 좋은 테스트는 아니다. 요구사항을 증명하는 검증이어야 한다.**

## 7. 테스트 데이터는 의도적으로 구성해야 한다

MyShelf의 Shelf 목록 조회 테스트에서는 사용자 A와 B가 같은 Shelf 이름을 사용하도록 구성했다.

```java
Shelf first = createShelf(userA, "같은 이름", "내 설명");

createShelf(userB, "같은 이름", "다른 사용자 설명");
```

이 데이터 구성에는 의미가 있다.

동일한 Shelf 이름이 서로 다른 사용자에게 존재할 수 있다는 비즈니스 규칙을 반영하면서, 조회 결과가 올바른 사용자 기준으로 분리되는지 확인할 수 있기 때문이다.

테스트 데이터를 무작정 많이 생성할 필요는 없다.

**검증하려는 규칙이 잘못 구현되었을 때 테스트가 실패하도록 데이터를 구성하는 것**이 중요하다.

예를 들어 사용자 A의 Shelf만 두 개 생성한다면 `userId` 필터가 누락된 버그를 발견하지 못할 수 있다.

반면 사용자 B의 Shelf를 함께 생성하면 사용자 격리 조건이 누락됐을 때 테스트가 실패할 가능성이 높아진다.

이를 위해 테스트를 설계할 때 다음 질문이 유용하다.

> 이 비즈니스 규칙을 일부러 잘못 구현한다면, 지금 작성한 테스트가 그 오류를 발견할 수 있을까?

## 8. 좋은 테스트의 추가 원칙

### 8.1 테스트는 독립적으로 실행할 수 있어야 한다

테스트 A가 실행되어야만 테스트 B가 성공하는 구조는 피한다.

각 테스트가 자신의 데이터와 필요한 상태를 준비하도록 구성한다.

### 8.2 테스트 데이터는 정리해야 한다

MyShelf에서는 실제 PostgreSQL을 사용하므로 테스트 데이터가 남으면 이후 테스트에 영향을 줄 수 있다.

현재 `ShelfReadIntegrationTest`는 `@AfterEach`에서 생성한 사용자와 Shelf 데이터를 삭제한다.

```java
@AfterEach
void cleanUp() {
    for (UUID userId : userIds) {
        jdbcTemplate.update(
            "delete from shelves where user_id = ?",
            userId
        );
        jdbcTemplate.update(
            "delete from users where id = ?",
            userId
        );
    }
}
```

FK 관계를 고려하여 자식 테이블인 `shelves`를 먼저 정리한다.

향후 `shelf_books`가 실제로 사용되면 테스트 데이터 정리 순서도 변경해야 할 수 있다.

또한 정리 코드는 테스트 중간에 실패하더라도 실행될 수 있도록 구성하는 것이 좋다.

현재 MyShelf처럼 트랜잭션 경계 자체를 검증해야 하는 테스트에서는 `@Transactional`을 통한 일괄 롤백이 적절하지 않을 수 있으므로, 데이터 정리 전략을 테스트 목적에 맞게 선택한다.

### 8.3 불필요한 실행 순서를 가정하지 않는다

현재 Shelf 목록 조회 API에 정렬 기준이 없다면 테스트에서도 특정 순서를 기대하지 않는다.

```java
.andExpect(
    jsonPath("$[*].id")
        .value(containsInAnyOrder(
            firstId.toString(),
            secondId.toString()
        ))
);
```

정렬 계약이 없는 상황에서 첫 번째 Shelf가 반드시 먼저 반환된다고 검증하면 DB 실행 계획 등에 따라 불안정한 테스트가 될 수 있다.

### 8.4 시간에 의존하는 검증을 주의한다

`createdAt`, `updatedAt`과 같은 시간값은 테스트 실행 시점에 영향을 받는다.

무조건 `Instant.now()`와 정확하게 일치하는지 비교하기보다는, 저장된 값과 응답 값이 일치하는지 검증할 수 있다.

시간에 따른 비즈니스 규칙 자체를 검증한다면 고정된 `Clock` 등을 사용하는 방법도 고려할 수 있다.

### 8.5 하나의 테스트가 무엇을 검증하는지 명확해야 한다

하나의 테스트 안에 여러 검증이 있어도 된다.

예를 들어 Shelf 단건 조회에서 상태 코드, ID, 이름, 설명, 생성일시를 함께 검증하는 것은 하나의 응답 계약을 확인하는 자연스러운 구성이다.

하지만 서로 관계없는 여러 비즈니스 규칙을 한 테스트에 몰아넣으면 실패 원인을 파악하기 어려워진다.

따라서 테스트 개수 자체보다 검증 목적이 명확한지를 우선한다.

## 9. 테스트를 작성할 때 사용할 체크리스트

새로운 API를 구현한 후 다음 질문을 순서대로 확인한다.

- [ ] 이 테스트에서 검증하려는 핵심 규칙은 무엇인가?
- [ ] 그 규칙을 검증하려면 어떤 사전 데이터가 필요한가?
- [ ] 실제로 실행해야 할 기능은 무엇인가?
- [ ] 정상 동작을 어떤 결과로 확인할 수 있는가?
- [ ] 데이터가 없거나 잘못된 요청이면 어떻게 되는가?
- [ ] 다른 사용자의 데이터에 접근하거나 영향을 줄 수 있는가?
- [ ] 실패한 쓰기 요청 이후 DB 상태는 유지되는가?
- [ ] 테스트가 정렬 순서나 현재 시각 등에 불필요하게 의존하지 않는가?
- [ ] 테스트들이 서로 독립적으로 실행되는가?
- [ ] 기존 테스트와 불필요하게 중복되는 검증은 없는가?

모든 API에서 모든 항목을 검증해야 한다는 뜻은 아니다.

기능의 특성과 위험에 따라 필요한 시나리오를 선택한다.

## 10. MyShelf에서의 적용 방향

향후 `updateShelf`, `deleteShelf`, `UserBook` 관리 기능에서도 같은 사고방식을 적용한다.

**먼저 비즈니스 규칙을 정의하고, 그 규칙을 확인할 수 있는 상황을 구성한 다음, 필요한 범위만 실행하고 결과를 검증한다.**

테스트 작성 순서는 다음과 같이 잡는다.

```text
요구사항 이해
    ↓
검증할 비즈니스 규칙 선정
    ↓
Given: 필요한 상황 및 데이터 준비
    ↓
When: 검증 대상 실행
    ↓
Then: 기대 결과 확인
    ↓
데이터 정리 및 테스트 독립성 확인
```

단위 테스트에서는 의존성을 Mock으로 대체해 특정 로직에 집중하고, 통합 테스트에서는 필요한 실제 구성요소를 연결해 동작을 확인한다.

테스트 시나리오 설계와 테스트 코드 작성은 구분할 수 있다.

반복적인 테스트 코드 구현을 AI에 맡기더라도, **어떤 규칙을 어떤 상황에서 검증할지 결정하고 결과의 타당성을 판단하는 능력**은 직접 길러야 한다.

## 11. 정리

이번 학습을 통해 가장 크게 이해한 내용은 다음과 같다.

**테스트 코드는 실제 사용 흐름을 그대로 재현하는 코드가 아니라, 검증하고 싶은 상황을 의도적으로 구성하는 코드다.**

그리고 좋은 테스트를 위해서는 다음이 중요하다.

1. 무엇을 검증하는지 명확히 정의한다.
2. 해당 규칙이 드러나도록 테스트 데이터를 구성한다.
3. 준비 단계와 실제 검증 대상 실행을 구분한다.
4. HTTP 응답뿐 아니라 필요한 경우 DB 상태도 검증한다.
5. 다른 사용자의 데이터, 경계 조건, 실패 이후 상태를 고려한다.
6. 테스트의 독립성과 결정성을 유지한다.
7. 테스트 개수를 늘리기보다 중요한 결함을 발견할 수 있도록 설계한다.

결국 **좋은 테스트를 작성하는 능력은 코드를 실행하는 방법뿐 아니라, 어떤 조건에서 코드가 잘못될 수 있는지 생각하는 능력**과 연결된다.

이는 테스트 작성에만 필요한 능력이 아니라, 실제 비즈니스 요구사항을 분석하고 안정적인 백엔드 기능을 설계하는 데도 도움이 된다.
