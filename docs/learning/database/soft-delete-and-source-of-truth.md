# 소프트 삭제 판단 기준: 관리 대상의 단일 기준과 상태 분산

## 1. 고민의 출발점

MyShelf에서 `UserBook`은 `(user_id, isbn)`으로 사용자별 도서를 식별하고, `ShelfBook`은 도서와 서재의 연결을 나타낸다.

**비즈니스 규칙:** 하나 이상의 `ShelfBook`에 연결된 `UserBook`만 사용자가 현재 관리하는 도서다. 마지막 서재에서 제거한 책은 관리 대상에서 빠진다. 재등록은 기존 UserBook을 재사용하고 요청 독서 상태를 적용하며, 메모가 null인 새 ShelfBook을 만든다.

마지막 연결이 삭제된 사실을 `UserBook.delete_yn`으로도 표시할지 고민했다.

## 2. 핵심 기준: 어떤 데이터가 상태를 결정하는가?

현재 관리 대상 여부는 **`ShelfBook` 연결 존재 여부 하나만으로 결정**된다.

```sql
SELECT EXISTS (
  SELECT 1
  FROM shelf_books
  WHERE user_book_id = :userBookId
);
```

여기에 `UserBook.delete_yn`을 추가하면 같은 사실을 다음 두 곳에서 표현하게 된다.

- `ShelfBook` 연결 있음/없음
- `UserBook.delete_yn = false/true`

예를 들어 마지막 `ShelfBook`이 삭제됐는데 `delete_yn = false`라면 상태가 불일치한다. Shelf 삭제 시 `ON DELETE CASCADE`가 실행되어도 `UserBook.delete_yn`은 자동으로 바뀌지 않는다.

**핵심 학습:** 같은 비즈니스 상태를 여러 곳에 저장하면 조회가 간편해질 수 있지만, 모든 변경 경로에서 상태를 동기화할 책임이 생긴다. 이를 피하려면 *단일 진실 공급원(Single Source of Truth)*을 정하고, 나머지 상태는 가능한 한 계산해 사용한다.

## 3. MyShelf에서의 선택

| 상황 | 처리 |
|---|---|
| 일부 서재에서 책 제거 | 공유 독서 상태와 다른 ShelfBook의 메모 유지. 삭제한 연결의 메모는 함께 제거 |
| 마지막 서재에서 제거 | UserBook은 보존하지만 관리 대상에서 제외 |
| 연결 0건인 책 재등록 | 기존 행을 재사용하며 [Feature 5의 등록 정책](../../planning/feature-5-book-management.md#36-등록-시-독서-상태와-재등록-처리)에 따라 처리 |
| 전체 도서 목록 조회 | `EXISTS`로 연결이 있는 UserBook만 조회할 계획. API는 Feature 6 범위 |

따라서 현 단계에서는 **`delete_yn`을 추가하지 않고 ShelfBook 존재 여부를 기준으로 판단**하기로 했다. `shelf_books.user_book_id` 인덱스도 이미 존재한다.

메모는 이제 UserBook이 아닌 ShelfBook에 속하므로, 등록 코드에서 연결 0건을 조회해 UserBook 메모를 초기화할 필요가 없다. 독서 상태 적용과 새 연결 생성은 Writer의 트랜잭션으로 묶는다. 전체 목록의 포함 조건과 등록 분기를 혼동하지 않는다.

## 4. 소프트 삭제가 적절한 경우

소프트 삭제가 나쁜 설계라는 뜻은 아니다. **삭제 자체가 독립적인 비즈니스 상태**라면 유용하다.

- 삭제된 항목을 복원하거나 별도 목록에서 관리해야 할 때
- 삭제 시각·사유 또는 감사 이력을 보존해야 할 때
- 연결 여부와 관계없이 활성/삭제 상태를 독립적으로 유지해야 할 때

이 경우에는 삭제 플래그를 상태의 기준으로 삼고, 조회 조건·유니크 제약·복원 정책·연관 데이터 처리까지 일관되게 설계해야 한다.

## 5. 정리

**소프트 삭제 도입 여부보다 먼저 물어볼 질문:**

> '삭제됨'이 별도로 저장해야 할 비즈니스 사실인가, 아니면 이미 존재하는 관계 데이터에서 계산할 수 있는 상태인가?

MyShelf에서는 현재 후자에 해당하므로 `ShelfBook`의 존재 여부를 관리 대상의 단일 기준으로 선택했다. 요구사항이 바뀌면 이 결정도 재검토한다.
