# B-tree 인덱스의 원리와 효율 판단 기준

## 1. 핵심 원리

B-tree 인덱스는 **정렬된 키를 균형 트리 구조로 관리하여 탐색 범위를 줄이는 자료구조**다.

정렬된 배열에 대한 단순 이진 탐색은 아니며, 노드의 키를 비교하면서 하위 노드를 탐색한다.

인덱스 효율은 두 가지 관점에서 판단한다.

1. **탐색 효율**: 정렬 구조를 활용해 읽어야 할 데이터 범위를 얼마나 줄이는가?
2. **비용 대비 효과**: 줄어든 읽기 비용이 인덱스 탐색·데이터 접근·유지 비용보다 큰가?

## 2. 인덱스 효율을 결정하는 조건

| 판단 기준 | 유리한 조건 | 불리한 조건 |
|---|---|---|
| 데이터 규모 | 데이터가 많음 | 데이터가 매우 적음 |
| 선택도 | 조회 대상이 전체의 일부 | 조회 대상이 전체의 대부분 |
| 검색 조건 | 정렬된 키로 탐색 범위 축소 가능 | 탐색 범위 축소가 어려움 |
| 변경 빈도 | 조회 중심 | INSERT·UPDATE·DELETE 빈번 |
| 유지 비용 | 조회 이득이 유지 비용보다 큼 | 유지 비용이 조회 이득보다 큼 |

### 2.1. 데이터 규모와 분포

아래 검색 예제는 해당 컬럼에 인덱스가 있다고 가정한 설명이며, 실제 인덱스 추가·성능 측정 결과는 아니다.

**데이터가 적은 경우**

테이블에 데이터가 10건뿐이라면 B-tree를 탐색하는 것보다 전체 데이터를 읽는 것이 빠를 수 있다.

**중복도가 높거나 데이터가 편중된 경우**

```sql
SELECT *
FROM user_books
WHERE reading_status_code = 'WANT_TO_READ';
```

전체 도서의 90%가 해당 상태라면 인덱스를 사용하더라도 대부분의 데이터를 읽어야 한다.

반대로 1%만 해당하는 상태를 조회한다면 인덱스가 유리할 가능성이 높다.

이를 판단할 때 중요한 개념이 **선택도(Selectivity)**다.

검색 조건이 얼마나 적은 행을 선별하는지가 중요하며, 특정 비율을 넘으면 무조건 인덱스가 불리하다는 절대적인 기준은 없다.

참고로 데이터가 편중되어도 B-tree 자체는 균형을 유지한다. 문제는 트리의 불균형이 아니라 검색 결과의 비율이다.

**NULL이 많은 경우**

```sql
-- 전체 데이터의 90%가 NULL이라고 가정
SELECT *
FROM shelves
WHERE description IS NULL;
```

PostgreSQL의 B-tree는 NULL도 인덱싱하며 `IS NULL`, `IS NOT NULL` 검색에도 활용할 수 있다.

다만 NULL이 전체의 90%라면 `IS NULL` 검색의 인덱스 효율은 낮을 수 있다. 반대로 소수의 `IS NOT NULL` 데이터를 조회한다면 유리할 수 있다.

즉, **NULL 자체가 문제가 아니라 해당 조건으로 조회되는 데이터의 비율이 중요하다.**

참고로 PostgreSQL의 일반 UNIQUE 제약조건은 기본적으로 여러 NULL을 허용한다. 이는 인덱스 검색 성능과 별개의 데이터 정합성 문제다.

### 2.2. 검색 조건과 정렬 구조

| 검색 조건 | B-tree 활용 | 이유 |
|---|---|---|
| `id = 10` | 유리 | 특정 키 탐색 |
| `created_at >= ?` | 유리 | 정렬된 범위 탐색 |
| `ORDER BY created_at` | 유리할 수 있음 | 인덱스 정렬 순서 활용 |
| `LIKE 'Java%'` | 조건부 유리 | 접두어 기반 범위 탐색 |
| `LIKE '%Java%'` | 일반적으로 불리 | 시작 위치를 특정할 수 없음 |
| `LOWER(title) = ?` | 일반 인덱스로는 어려움 | 인덱싱된 표현식과 검색 표현식 불일치 |

`LIKE 'Java%'`는 PostgreSQL의 Collation 및 인덱스 연산자 클래스에 따라 활용 여부가 달라진다.

`LOWER(title)`은 별도의 표현식 인덱스로 대응할 수 있다.

**복합 인덱스의 컬럼 순서**

```sql
UNIQUE (shelf_id, user_book_id)
```

- `WHERE shelf_id = ?` → 선행 컬럼을 통한 효율적인 탐색
- `WHERE shelf_id = ? AND user_book_id = ?` → 두 컬럼을 활용한 탐색
- `WHERE user_book_id = ?` → 선행 컬럼 조건이 없어 효율이 떨어질 수 있음

복합 인덱스에서는 특히 선행 컬럼의 동등 조건과 범위 조건이 중요하다.

### 2.3. 데이터 변경과 인덱스 유지 비용

인덱스는 조회 성능을 개선하지만 데이터를 변경할 때 유지 비용이 발생한다.

| 작업 | 비용 |
|---|---|
| INSERT | 인덱스 항목 추가 |
| UPDATE | 변경 내용에 따라 인덱스 갱신 |
| DELETE | 삭제된 행의 인덱스 항목에 대한 후속 정리 |
| SELECT | 적절한 인덱스를 활용하면 조회 비용 감소 |

예를 들어 독서 상태가 자주 변경되는 테이블에서 `reading_status_code`에 인덱스를 추가하면 UPDATE 비용이 증가할 수 있다.

PostgreSQL에서는 인덱스가 참조하지 않는 컬럼을 수정할 때 HOT(Heap-Only Tuple) 최적화를 활용할 수 있지만, 인덱스에 포함된 컬럼의 변경은 이를 제한할 수 있다.

따라서 **조회 빈도와 데이터 변경 빈도를 함께 고려해야 한다.**

## 3. MyShelf의 현재 적용과 후속 검토

### 현재 적용: 사용자별 Shelf 이름과 목록 조회

```sql
UNIQUE (user_id, name)
```

V2 마이그레이션은 이 제약조건을 추가하고 기존 `idx_shelves_user_id` 단일 인덱스를 제거한다. 생성된 복합 인덱스는 사용자별 이름 중복을 방지하며, 선행 컬럼인 `user_id`를 사용하는 Shelf 목록 조회에도 활용할 수 있다. 실제 인덱스 선택과 성능 개선 여부는 실행 계획으로 확인해야 한다.

### Feature 5 적용: Shelf별 도서 조회

Shelf별 목록 API와 JOIN FETCH·기본 정렬은 Feature 5에서 구현했다. 아래는 기존 UNIQUE 인덱스의 활용 가능성을 설명하며, 실행 계획이나 성능 개선을 측정한 결과는 아니다. 실제 조회 구조는 [도서 관리 문서](../../architecture/book-management.md#5-목록-조회와-모델-변환)를 참고한다.

```sql
UNIQUE (shelf_id, user_book_id)
```

- 동일 Shelf 내 도서 중복 등록 방지
- Shelf별 도서 목록 조회에 활용 가능
- UNIQUE 제약조건으로 생성된 인덱스 재사용 가능

### Feature 6 후속 검토: 내 서재 도서 검색

다음은 사용자 조건과 문자열 포함 검색을 설명하기 위한 단순화한 SQL이다.

```sql
SELECT *
FROM user_books
WHERE user_id = :userId
  AND title ILIKE '%자바%';
```

일반 B-tree는 문자열 포함 검색에 불리하다.

검색 데이터가 많아지고 실제 병목이 확인되면 PostgreSQL의 `pg_trgm` 확장과 GIN 인덱스를 검토할 수 있다.

최종 검색 SQL은 인증된 사용자 UUID를 조건에 전달하고, `shelf_books`에 연결된 도서만 조회하도록 구성해야 한다. 특정 Shelf를 조회한다면 해당 Shelf의 소유권도 확인한다.

## 4. 실무 판단 원칙

**인덱스가 존재한다고 반드시 사용되는 것은 아니며, 사용된다고 반드시 빠른 것도 아니다.**

PostgreSQL은 데이터 통계와 예상 비용을 바탕으로 실행 계획을 결정한다.

실제 SQL과 데이터 분포를 확인하고, 다음 명령으로 성능을 검증한다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM shelves
WHERE user_id = :userId;
```

`:userId`는 조회할 실제 UUID로 바인딩하거나 치환한다. 인덱스 적용 전후 실행 계획과 실행 시간을 비교한다. 이 문서에서는 실행 계획 측정을 수행하지 않았다.

스키마별 설계 배경은 [데이터베이스 설계 학습](database-design.md)을 참고한다.

---

## 결론

B-tree 인덱스의 효율은 결국 두 가지로 판단한다.

**1. 탐색 효율:** 정렬된 트리를 활용해 읽어야 할 데이터 범위를 충분히 줄일 수 있는가?

**2. 비용 대비 효과:** 조회 성능의 이득이 탐색·데이터 접근·인덱스 유지 비용보다 큰가?

이 두 가지를 기준으로 데이터 규모, 선택도, 검색 조건, 변경 빈도를 검토한다.
