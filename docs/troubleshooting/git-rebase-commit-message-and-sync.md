# Git Rebase로 과거 커밋 메시지 수정 및 다중 PC 이력 동기화

## 1. 문제 상황

MyShelf의 `feature/4-shelf-management` 브랜치에서 Shelf 목록 및 상세 조회 기능을 구현한 뒤, 해당 커밋의 메시지 유형이 잘못 작성된 것을 발견했다.

기존 커밋 메시지:

```text
fix: Shelf 목록 및 상세 조회 기능 구현
```

변경하려는 메시지:

```text
feat: Shelf 목록 및 상세 조회 기능 구현
```

해당 작업은 기존 버그를 수정한 것이 아니라 새로운 조회 기능을 구현한 것이므로 `fix`보다 `feat`가 적절하다.

문제는 대상 커밋 `8b8968f`가 이미 GitHub에 Push되었고, 그 이후에도 여러 커밋이 생성되었다는 점이다.

또한 MyShelf는 회사 Windows PC와 집 MacBook에서 동일한 기능 브랜치로 작업하고 있었다.

## 2. 원인과 고려사항

### 2.1 이미 Push한 커밋 메시지 변경

Git 커밋의 해시는 커밋 메시지, 부모 커밋 등의 정보를 바탕으로 계산된다.

따라서 커밋 메시지를 수정하면 기존 커밋을 직접 변경하는 것이 아니라 새로운 해시를 가진 커밋을 생성한다.

```text
변경 전

A ── B ── C ── D
     ↑
    fix

변경 후

A ── B' ── C' ── D'
     ↑
    feat
```

B의 메시지를 수정하면 B'가 만들어지고, 이를 부모로 참조하는 후속 커밋도 재작성된다.

이 때문에 기존 원격 이력을 유지하는 일반적인 Push로는 변경된 이력을 반영할 수 없다.

### 2.2 다중 PC의 이력 불일치

회사 PC에서 Rebase한 커밋을 강제 Push하면 GitHub는 새로운 이력을 가리키게 된다.

그러나 집 MacBook에는 변경 전 커밋이 그대로 남아 있을 수 있다.

```text
집 MacBook
A ── B ── C ── D

GitHub
A ── B' ── C' ── D'
```

이 상태에서 집 PC가 기존 이력을 단순히 Merge하면 이전 커밋과 새로운 커밋을 모두 연결하는 불필요한 Merge Commit이 생성될 수 있다.

따라서 원격 이력이 재작성된 경우에는 일반적인 신규 커밋 동기화와 구분해서 처리해야 한다.

## 3. 해결 과정

### 3.1 작업 상태 확인 및 임시 보관

Rebase 전에 작업 브랜치와 미커밋 변경사항을 확인한다.

```bash
git status
```

작업 중인 변경사항이 있다면 먼저 커밋하거나 Stash로 보관한다.

Untracked 파일까지 포함해야 한다면:

```bash
git stash push -u -m "WIP: 학습 문서 작성"
```

`-u`는 Untracked 파일을 포함하며, `-m`은 Stash 메시지를 지정한다.

Stash를 사용했다면 `git stash list`와 `git status`로 보관 상태를 확인한다.

### 3.2 Interactive Rebase 실행

메시지를 수정할 대상 커밋은 `8b8968f`였다.

```bash
git rebase -i 8b8968f^
```

여기서 `^`는 해당 커밋의 첫 번째 부모를 의미한다.

Interactive Rebase는 지정한 기준 커밋 이후의 이력을 편집 대상으로 사용한다.

따라서 대상 커밋 자체를 포함하려면 그 부모 커밋을 기준으로 지정해야 한다.

### 3.3 reword로 메시지 변경

편집기에서 수정할 커밋의 `pick`을 `reword`로 변경한다.

```text
reword 8b8968f fix: Shelf 목록 및 상세 조회 기능 구현
pick d12e9b8 ...
pick 05af096 ...
```

첫 번째 편집 화면은 **어떤 커밋에 어떤 작업을 수행할지 지정하는 단계**다.

저장 후 열린 두 번째 메시지 편집 화면에서 실제 커밋 메시지를 변경한다.

```text
feat: Shelf 목록 및 상세 조회 기능 구현
```

이후 Rebase가 진행되면서 대상 커밋과 후속 커밋이 재작성된다.

### 3.4 원격 브랜치 갱신

Rebase 완료 후 커밋 이력을 확인한다.

```bash
git log --oneline -6
git status
```

변경된 이력을 원격에 반영한다.

```bash
git push --force-with-lease origin feature/4-shelf-management
```

`--force-with-lease`는 실제 원격 브랜치가 로컬에서 예상한 상태일 때만 강제 갱신을 허용한다.

일반적인 `--force`보다 안전하지만, 모든 이력 손실을 방지하는 것은 아니므로 사용 전에 원격 상태와 다른 작업자의 변경 여부를 확인해야 한다.

**회사 PC에서 Rebase와 Force Push까지 진행한 상태다.**

Stash를 사용했다면 이후 필요한 시점에 다음 명령으로 변경사항을 복원한다.

```bash
git stash pop
```

## 4. 집 MacBook의 이력 동기화

회사 PC에서 이미 재작성한 이력을 GitHub에 반영했으므로 집 MacBook에서도 새 이력으로 동기화해야 한다.

이 작업은 회사 PC에서의 Force Push와 별개로 수행한다.

### 4.1 동기화 전 확인

집 MacBook에서 해당 기능 브랜치로 이동한다.

```bash
git switch feature/4-shelf-management
git status
git fetch origin
```

이후 로컬과 원격 추적 브랜치의 커밋 차이를 확인한다.

```bash
git log --oneline HEAD..origin/feature/4-shelf-management

git log --oneline origin/feature/4-shelf-management..HEAD
```

첫 번째 명령은 원격 추적 브랜치에서만 도달할 수 있는 커밋을, 두 번째 명령은 로컬 HEAD에서만 도달할 수 있는 커밋을 보여준다.

Rebase 전의 기존 커밋이 두 번째 명령에 나타날 수 있으므로, 출력됐다는 이유만으로 새로운 로컬 작업이 있다고 단정하지 않는다.

### 4.2 reset --hard로 동기화

현재 확인된 상황에서는 집 PC에만 존재하는 미Push 커밋이 없고 회사 PC가 최신 작업을 가지고 있다.

집 PC에서도 미커밋 변경사항이나 보존해야 할 로컬 커밋이 없는지 최종 확인한 뒤 다음 명령을 사용할 수 있다.

```bash
git reset --hard origin/feature/4-shelf-management
```

이 명령은 현재 로컬 브랜치와 Staging Area, 추적 중인 작업 파일을 원격 추적 브랜치가 가리키는 상태로 맞춘다.

```text
동기화 전

집 MacBook: A ─ B ─ C ─ D
GitHub:     A ─ B'─ C'─ D'

동기화 후

집 MacBook: A ─ B'─ C'─ D'
GitHub:     A ─ B'─ C'─ D'
```

이 과정에서 새로운 Merge Commit은 생성되지 않는다.

단, `reset --hard`는 미커밋 변경사항을 버릴 수 있으며 로컬 전용 커밋을 현재 브랜치에서 제외하므로 사전 확인이 필수다.

**집 MacBook에서의 동기화 완료 여부는 실제 실행 및 검증 후 기록한다.**

## 5. 왜 일반 Merge를 사용하지 않았는가?

일반적인 신규 커밋 동기화라면 다음과 같이 Fast-forward가 가능하다.

```text
로컬: A ─ B
원격: A ─ B ─ C
```

이 경우 `git pull --ff-only` 또는 Fetch 이후 Fast-forward Merge로 충분하다.

그러나 Rebase 이후에는 기존 커밋과 새 커밋이 서로 다른 해시를 가진다.

```text
        B ─ C ─ D        기존 로컬 이력
       /
A ───
       \
        B'─ C'─ D'       재작성된 원격 이력
```

이 상태에서 Merge하면 Git은 서로 갈라진 이력을 병합하려고 한다.

파일 내용에 충돌이 없더라도 기존 커밋과 재작성된 커밋이 모두 이력에 포함될 수 있다.

이번 작업의 목적은 기존 커밋 메시지를 수정하고 해당 이력을 대체하는 것이므로, 보존할 로컬 작업이 없는 집 PC에서는 Merge보다 Reset이 적절하다.

## 6. 주의사항 및 재발 방지

이번 작업을 통해 다음 사항을 확인했다.

1. **커밋 메시지도 커밋 해시에 영향을 준다.** 메시지만 변경해도 커밋 이력이 재작성될 수 있다.
2. **공유된 이력의 Rebase는 주의해야 한다.** 이미 Push한 커밋을 수정하면 다른 PC나 협업자의 로컬 이력과 달라진다.
3. **원격 추적 브랜치는 로컬에 존재한다.** `origin/feature/...`는 서버에 직접 존재하는 참조가 아니라 Fetch로 갱신되는 로컬 참조다.
4. **일반적인 동기화와 이력 재작성 후 동기화는 다르다.** 새 커밋 추가에는 Fast-forward가 적절할 수 있지만, 이력 재작성 후에는 기존 커밋을 유지할지 먼저 판단해야 한다.
5. **`reset --hard` 전에 로컬 작업을 확인한다.** 무조건 실행하지 않고 작업 파일과 로컬 전용 커밋을 검토한다.
6. **강제 Push에는 `--force-with-lease`를 우선 고려한다.** 단, 원격 추적 브랜치의 최신 상태가 언제 어떻게 갱신됐는지도 주의해야 한다.
7. **커밋 유형을 먼저 검토한다.** 신규 기능 구현은 `feat`, 기존 버그 수정은 `fix`를 사용하여 불필요한 이력 수정을 줄인다.

## 7. 결과 및 학습

MyShelf의 Shelf 목록 및 상세 조회 기능 커밋을 `fix`에서 `feat`으로 수정하기 위해 Interactive Rebase의 `reword`를 사용했다.

회사 PC에서 변경된 이력을 `--force-with-lease`로 Push하는 작업까지 진행했다.

집 MacBook의 로컬 이력 동기화는 별도로 수행하고 결과를 확인할 예정이다.

이번 경험을 통해 다음 개념을 이해했다.

- Rebase는 커밋 이력을 재작성한다.
- Reset은 현재 브랜치가 가리키는 위치를 변경한다.
- 원격 추적 브랜치는 마지막으로 가져온 원격 브랜치 상태를 나타낸다.
- 이력이 재작성됐을 때는 단순 Merge가 항상 적절한 해결책은 아니다.
- Git 명령어 실행 전에 어떤 커밋과 작업 파일이 영향을 받는지 확인해야 한다.

**핵심은 명령어 자체보다 현재 로컬·원격의 커밋 관계를 이해하고, 보존해야 할 이력이 있는지 판단한 뒤 적절한 동기화 방식을 선택하는 것이다.**
