# 문서 구성 및 관리 가이드

## 1. 목적

문서마다 답할 질문과 수정할 기준점을 정한다. 문서 리팩터링은 이 가이드를 기준으로 중복 설명을 줄이고, 기존 학습·결정·장애 기록의 근거를 보존하는 방향으로 진행한다.

문서 수를 줄이는 것 자체를 목표로 하지 않는다. 기능 상태·설정값·테스트 수는 이 가이드에 복사하지 않는다. AI 협업·명령 실행 권한은 [AGENTS.md](../AGENTS.md), Git 작업은 [Git 작업 규칙](git-workflow.md)을 따른다.

## 2. 문서별 책임

| 위치 | 답하는 질문 | 변경할 때의 기준 |
|---|---|---|
| 루트 `README.md` | 어떤 프로젝트이며 어떻게 시작하는가? | 개요·기능 요약·로컬 시작 방법과 문서 안내를 유지한다. 상세 설계·검증 이력을 반복하지 않는다. |
| `planning/` | 무엇을 왜 만들고, 어디까지 완료해야 하는가? | 현행 정책과 진행 중인 계획은 갱신한다. 완료된 Feature는 당시 범위·정책·완료 결과를 보존한다. |
| `planning/roadmap.md` | 무엇을 진행했고 다음에 무엇을 하는가? | 상태를 요약하고 기능별 계약·검증 기록으로 연결한다. |
| `architecture/` | 현재 구현이 어떻게 구성되고 동작하는가? | 책임·의존성·처리 흐름·현재 한계를 코드와 대조한다. 과거 실행 결과는 검증 기록으로 연결한다. |
| `database/` | 데이터의 구조와 제약은 무엇인가? | 스키마 설명을 관리한다. 실제 정의는 Flyway SQL이 기준이다. |
| `decisions/` | 왜 이 대안을 선택했는가? | 결정 당시 대안·근거·트레이드오프를 보존한다. 변경·대체된 결정은 후속 문서로 연결한다. |
| `learning/` | 어떤 원리를 어떻게 이해·실험했는가? | 원리·예제·측정·검증 과정을 보존한다. 현재 구현 전체를 중복 명세하지 않는다. |
| `troubleshooting/` | 실제로 무엇이 실패했고 어떻게 해결했는가? | 당시 환경·증상·확인한 원인·해결·결과를 보존한다. 현재 재현 절차와 과거 명령을 구분한다. |

문서의 분류와 별개로 **현재도 유효해야 하는 설명**과 **당시 과정을 보존하는 기록**을 구분한다. 현행 정책·Architecture·Database·README·현재 실행 안내는 관련 변경에 맞춰 갱신한다. 완료된 Feature·ADR·Learning·Troubleshooting의 당시 판단과 결과는 보존하며, 사실 오류와 깨진 링크는 정정한다.

Learning의 개념 예제는 실제 코드와 같을 필요가 없다. 당시 구현·실험 예제는 설정값을 최신 값으로 덮어쓰지 않고, 오해할 가능성이 있을 때만 기준 시점과 현재 문서 링크를 붙인다. 현재 실행 안내로 제공하는 명령은 계속 관리한다. 같은 명령을 과거 기록과 현행 절차로 동시에 취급하지 않는다.

## 4. 중복과 변경을 관리하는 방법

1. **같은 사실의 기준점을 정한다.** 정책은 Planning, 현재 처리 구조는 Architecture에 둔다. 설정·워크플로·스크립트의 실제 동작은 해당 원본과 대조하고, 문서는 의미와 제약을 설명한다. API 계약은 Controller·DTO·검증 코드와 생성 OpenAPI를 확인하며 별도 전체 명세를 중복 유지하지 않는다.
2. **요약과 중복 명세를 구분한다.** 이해에 필요한 짧은 요약은 허용한다. 다른 문서에도 같은 표·전체 설정·전체 절차를 복사해 각각 최신화하는 방식은 피한다. 개념을 설명하는 발췌 코드는 목적과 기준 시점을 밝힌다.
3. **기록의 맥락을 보존한다.** 과거 환경·로그·실행 결과를 현재 동작처럼 바꾸지 않는다. 필요한 경우 “본문은 당시 기록이며 현재 구성은 관련 아키텍처 참고”라는 안내를 둔다. 독립적인 판단·사례가 없는 문서만 통합을 검토한다.
4. **구현과 검증을 구분한다.** 코드 존재, Mock 테스트, 실제 DB·Redis 통합 검증, CI, 이미지 게시, 실제 배포를 각각 기록한다. 실행일·환경·대상을 남기고 미확인 결과를 완료 처리하지 않는다. 비밀값은 기록하지 않는다.
5. **구현과 의도가 다르면 차이를 드러낸다.** 코드에 맞추기 위해 비즈니스 정책을 임의로 바꾸거나, 문서를 맞추기 위해 코드를 수정하지 않는다. 불일치와 미결정을 명시하고 필요한 판단을 별도로 진행한다.

예를 들어 도서 등록 정책 변경은 현행 도서 관리 정책부터 확인하고, 처리 흐름이 바뀌면 도서 관리 아키텍처를 수정한다. Feature 5와 과거 JPA 실험 결과는 보존한다. 타임아웃 값 변경은 실제 설정과 검색 아키텍처의 관련 설명을 확인하며, 과거 측정 결과를 새 값의 결과로 고쳐 쓰지 않는다.

코드·설정에 명확한 수치나 메서드 목록을 모두 문서에 복사할 필요는 없다. 문서는 정책의 의미·책임 경계·선택 이유·제약에 집중하고, 구체적인 값은 설명에 꼭 필요한 경우에만 유지한다.

### 변경 유형별 기본 확인 대상

| 변경 유형 | 먼저 확인할 문서 |
|---|---|
| 도서 등록·중복·삭제·독서 상태 등 업무 규칙 | 현행 도서 관리 정책 |
| API 경로·응답 또는 인증·캐시·처리 흐름 | 해당 Architecture. 상세 API 계약은 Controller·DTO·생성 OpenAPI |
| 테이블·컬럼·제약·인덱스 | Flyway SQL과 Database |
| 환경변수·로컬 실행 방식 | README와 해당 실행 안내 |
| 배포·운영 조회 방식 | CI/CD Architecture와 [EC2 운영 검증 명령](learning/infrastructure/ec2-automated-deployment.md#6-운영-환경-검증-명령) |
| 중요 설계 결정 | 현재 설명을 갱신하고, 기록할 가치가 있을 때 후속 ADR |
| 학습 내용·과거 원인 분석의 오류 | 해당 Learning·Troubleshooting |
| 기능 진행 상태·향후 범위 | 로드맵과 진행 중인 Feature 계획 |

이 표는 모든 변경에 적용하는 전체 체크리스트가 아니다. 단순 내부 리팩터링으로 설명한 책임·흐름이 바뀌지 않았다면 문서를 수정할 필요가 없을 수 있다. 먼저 변경 사실과 책임 문서를 확인하고, 관련 키워드·식별자로 `rg -n` 검색을 보완한다. 검색 결과의 현행 설명은 수정하고 과거 기록은 보존 여부를 판단한다. 전역 정책 변경은 여러 문서에 영향을 줄 수 있으며 검색만으로 누락 방지를 보장하지 않는다.

예를 들어 TTL 변경 시 `rg -n "TTL|만료|Duration.ofMinutes" docs/`로 관련 설명을 찾되, 과거 실험의 숫자를 일괄 치환하지 않는다. 학습 문서에 현재 운영 절차를 함께 둔 경우에는 해당 절차만 갱신한다.

## 5. 리팩터링과 검토

- CI/CD, 도서, 인증·DB처럼 주제별로 관련 문서를 살피고 기준 문서를 먼저 정리한다. 파일 이동·삭제부터 시작하지 않는다.
- 다른 문서는 고유한 원리·선택 이유·검증 결과를 남기고, 중복된 현재 명세를 요약과 상대 링크로 바꾼다. 링크만 남겨 문서의 맥락이 사라지지 않도록 한다.
- 제목·파일을 변경하면 참조도 수정한다. 상대 링크·제목 앵커·코드 블록과 `git diff --check`를 확인한다. 링크 검사는 내용과 구현의 일치까지 보장하지 않는다.
- 문서만 수정했다면 빌드·배포를 실행한 것으로 보고하지 않는다. 명령 예제를 변경했을 때 실제 실행 여부도 구분한다.
- 다음 실제 기능 변경에서 확인·수정한 문서와 누락을 살핀다. 문제가 반복될 때만 구조나 자동 검증을 추가한다. 링크·코드 경로 검사는 명확한 오류를 찾는 데 사용하며, 모든 과거 예제의 컴파일이나 문서의 의미 검증을 요구하지 않는다.

완료 기준은 문서 개수가 아니라 **찾아갈 기준점이 명확하고, 중복된 현재 명세가 줄었으며, 과거 근거와 참조가 보존되었는가**이다.

## 6. 에이전트에게 문서 갱신을 요청하는 방법

기능 추가·수정·리팩터링 후에는 다음 요청을 사용한다. 변경 목적과 비교할 커밋·브랜치가 있으면 함께 명시한다.

```text
이번 변경의 코드·테스트·diff를 확인하고, docs/documentation-guide.md에 따라 필요한 문서를 보완해줘.
관련 키워드를 검색해 영향을 확인하고, 현행 설명과 과거 기록을 구분해 처리해줘.
실행하지 않은 검증 결과는 추가하지 말고, 수정한 문서·이유·확인 결과를 보고해줘.
코드·설정과 Git 상태는 변경하지 마.
```

전체 정합성 점검이 필요할 때는 첫 문장을 다음과 같이 바꾼다. 평소 변경 후 갱신에서는 전체 문서 점검을 기본으로 요구하지 않는다.

```text
현재 코드·테스트·설정과 README·docs 전체를 대조하고, docs/documentation-guide.md에 따라 필요한 문서를 보완해줘.
```

수정 없이 검토만 원한다면 “필요한 문서를 보완해줘”를 “수정이 필요한 문서와 이유를 알려주고, 파일은 변경하지 마”로 바꾼다. 어느 요청이든 저장소의 AGENTS.md에 정한 실행 권한을 따른다.
