# MyShelf CI/CD 아키텍처

> 상태: 설계 초안 (구현 전)
> 작성일: 2026-10-21
> 범위: CI 구축 및 향후 CD 확장 방향

## 1. 개요

MyShelf는 로컬 개발 환경에서 Docker와 PostgreSQL을 이용하여 애플리케이션을 실행하고 테스트하고 있다.

현재는 개발자가 로컬에서 직접 빌드와 테스트를 실행하여 변경사항을 검증한다.

향후 코드 변경사항에 대한 검증을 자동화하고, 검증된 애플리케이션을 일관된 방식으로 빌드 및 배포할 수 있도록 CI/CD 파이프라인을 단계적으로 구축한다.

### 1.1 도입 목적

- 개발자 로컬 환경에 의존하지 않는 빌드 및 테스트 환경 확보
- Pull Request 단위의 자동화된 코드 검증
- PostgreSQL 통합 테스트의 독립성과 재현성 확보
- 검증된 애플리케이션의 Docker 이미지 빌드 및 게시 자동화
- 향후 운영 환경에 대한 배포 자동화 기반 마련

CI는 코드의 품질을 완전히 보장하는 수단이 아니라, 사전에 정의한 검증 절차를 일관되게 수행하는 수단으로 활용한다.

## 2. 현재 개발 및 테스트 환경

### 2.1 로컬 실행 환경

MyShelf는 Docker Compose를 이용하여 PostgreSQL을 실행한다.

현재 개발용 데이터베이스와 테스트용 데이터베이스는 동일한 PostgreSQL 컨테이너 내부에 논리적으로 분리되어 있다.

| 구분 | 환경 | 목적 |
|---|---|---|
| 개발 | `local` 프로필 / `myshelf` | 로컬 개발 및 기능 확인 |
| 테스트 | `test` 프로필 / `myshelf_test` | 자동화 테스트 |
| DB 실행 | Docker Compose | PostgreSQL 컨테이너 관리 |
| 스키마 관리 | Flyway | 데이터베이스 마이그레이션 |

테스트용 데이터베이스는 Docker 초기화 구성을 통해 생성한다.

개발 데이터베이스와 테스트 데이터베이스를 분리하여 테스트 데이터가 개발 데이터에 영향을 주는 것을 방지한다.

### 2.2 현재 테스트 구성

- Gradle을 이용하여 테스트 실행
- Spring Boot의 `test` 프로필 사용
- H2 대신 PostgreSQL을 이용한 통합 테스트
- Flyway를 이용한 데이터베이스 스키마 관리
- 최근 로컬 검증 기준 전체 32개 테스트 통과

현재까지의 검증은 개발자 로컬 환경을 기준으로 수행되었다.

CI 도입 시 동일한 테스트 코드를 독립적인 실행 환경에서도 검증한다.

## 3. CI/CD 구축 전략

CI/CD는 한 번에 구축하지 않고 다음 단계로 나누어 진행한다.

| 단계 | 주요 작업 | 구분 |
|---|---|---|
| 1 | GitHub Actions 기반 빌드 및 테스트 자동화 | 현재 설계 대상 |
| 2 | Docker 이미지 빌드 및 이미지 저장소 게시 | 후속 작업 |
| 3 | Jenkins를 활용한 CI 파이프라인 실습 | 후속 학습 |
| 4 | 운영 환경 구성 및 배포 자동화 | 핵심 기능 개발 이후 |

1~3단계는 프로젝트 로드맵의 CI 및 배포 기반 구축 단계에 해당한다.

4단계는 운영 배포 및 CD 구축 단계에서 진행한다.

실제 배포 대상, 인프라 구성, 배포 방식 등은 CD 구현 시점에 별도로 결정한다.

## 4. GitHub Actions 기반 CI 설계

### 4.1 CI 도구

GitHub Actions를 MyShelf의 주 CI 도구로 사용한다.

선정 배경은 다음과 같다.

- GitHub 저장소 및 Pull Request와 직접 연동 가능
- 별도의 Jenkins 서버 구축 없이 CI 실행 가능
- Workflow를 YAML 파일로 정의하고 버전 관리 가능
- 서비스 컨테이너를 이용한 PostgreSQL 테스트 환경 구성 가능

Jenkins는 CI/CD 도구의 동작 원리와 운영 방식 비교를 위한 학습 대상으로 활용한다.

별도의 Jenkins 운영 환경을 현재 프로젝트의 필수 구성요소로 두지는 않는다.

### 4.2 CI 실행 시점

초기 Workflow는 다음 이벤트를 기준으로 실행하도록 설계한다.

| 이벤트 | 목적 |
|---|---|
| `pull_request` → `main` | 병합 전 변경사항 검증 |
| `push` → `main` | 병합 이후 메인 브랜치 검증 |
| `workflow_dispatch` | 필요할 때 수동 실행 |

Pull Request에서 실행되는 CI의 결과를 확인하여 병합 여부를 판단한다.

CI 자체가 병합을 차단하는 것은 아니며, 필수 상태 검사 및 브랜치 보호 정책을 적용해야 병합을 제한할 수 있다.

해당 정책은 CI 구축 후 별도로 검토한다.

### 4.3 CI 실행 구조

초기 CI는 다음 흐름을 목표로 한다.

1. 개발자가 GitHub에 Pull Request 생성
2. GitHub Actions Workflow 실행
3. GitHub 호스팅 Runner에서 소스 코드 체크아웃
4. Java 및 Gradle 실행 환경 준비
5. PostgreSQL 서비스 컨테이너 준비
6. Spring Boot `test` 프로필로 테스트 실행
7. Flyway 마이그레이션 및 테스트 수행
8. 빌드와 테스트 성공 여부를 GitHub에 표시

테스트 과정에서 실패가 발생하면 CI Job을 실패 처리한다.

초기 CI에서는 애플리케이션을 운영 환경에 배포하지 않는다.

### 4.4 실행 환경

GitHub Actions의 Ubuntu 기반 Runner를 사용한다.

Java 버전은 프로젝트의 Gradle 및 Java Toolchain 설정을 확인하여 결정한다.

PostgreSQL 버전은 기존 로컬 Docker 환경과의 호환성을 고려하여 선택한다.

버전은 Workflow에서 명시적으로 관리하고, 재현성을 높일 필요가 있는 주요 도구는 고정 버전 사용을 검토한다.

## 5. CI 테스트 데이터베이스 구성

### 5.1 기본 원칙

CI 환경은 개발자 로컬 데이터베이스에 연결하지 않는다.

GitHub Actions의 `services` 기능으로 CI 실행에 필요한 PostgreSQL 컨테이너를 준비한다.

로컬 환경과 CI 환경은 DB 준비 방식에 차이가 있지만, 동일한 `test` 프로필과 테스트 코드를 사용한다.

### 5.2 환경별 DB 구성

| 항목 | 로컬 | GitHub Actions |
|---|---|---|
| PostgreSQL 실행 | Docker Compose | Actions `services` |
| DB 이름 | `myshelf_test` | `myshelf_test` |
| Spring 프로필 | `test` | `test` |
| 스키마 초기화 | Flyway | Flyway |
| DB 수명 | 로컬 컨테이너 및 볼륨 설정에 따름 | 일반적으로 Job 종료 시 정리 |

GitHub Actions에서는 PostgreSQL 이미지의 `POSTGRES_DB` 설정을 활용하여 테스트용 데이터베이스를 생성하는 방식을 우선 검토한다.

기존 로컬 Docker 초기화 스크립트에 추가 사용자, 권한, 확장 기능 등 CI에서도 필요한 설정이 있는지 확인한 후 최종 구성을 결정한다.

### 5.3 테스트 설정 관리

테스트 프로필에 필요한 데이터베이스 연결 정보는 CI 실행 환경에서 명시적으로 제공한다.

- JDBC URL
- 데이터베이스 사용자
- 데이터베이스 비밀번호
- 그 외 테스트 실행에 필요한 환경변수

테스트용 임시 자격 증명과 실제 운영 비밀값은 구분한다.

운영 환경의 민감한 정보는 저장소에 직접 커밋하지 않는다.

### 5.4 Flyway 적용

CI에서 준비한 테스트 데이터베이스에는 Flyway를 이용하여 스키마를 생성한다.

테스트 실행에 필요한 테이블과 제약조건은 버전 관리되는 마이그레이션을 기준으로 구성한다.

이를 통해 기존 로컬 데이터베이스 상태에 의존하지 않고 통합 테스트를 실행하는 것을 목표로 한다.

## 6. CI 검증 기준

초기 CI 구축의 완료 기준은 다음과 같다.

- Pull Request 생성 시 Workflow가 자동 실행된다.
- 별도로 준비된 PostgreSQL 테스트 데이터베이스에 연결된다.
- Spring Boot `test` 프로필이 사용된다.
- Flyway 마이그레이션이 정상 수행된다.
- 기존 전체 테스트가 GitHub Actions에서 통과한다.
- 테스트를 의도적으로 실패시켰을 때 CI도 실패한다.
- 개발자 로컬 Docker 환경을 실행하지 않아도 CI가 동작한다.
- 환경 구성에 필요한 실제 운영 비밀값이 저장소에 노출되지 않는다.

최종 테스트 개수와 실행 결과는 CI 구축 완료 후 기록한다.

## 7. Docker 이미지 빌드 및 게시 계획

CI 검증이 완료되면 별도의 작업으로 Docker 이미지 빌드와 게시를 자동화한다.

목표 흐름은 다음과 같다.

1. 코드 변경사항 검증
2. Gradle 빌드 및 테스트 성공
3. Docker 이미지 빌드
4. 이미지 태그 생성
5. 컨테이너 이미지 저장소에 게시

이미지 저장소는 GitHub Container Registry(GHCR)를 우선 검토한다.

이미지 버전을 식별할 수 있도록 Git 커밋 식별자 등을 활용하는 태그 전략을 검토한다.

이미지 게시에 필요한 권한은 최소한으로 부여하고, 테스트 실패 시 검증되지 않은 이미지를 게시하지 않도록 구성한다.

구체적인 Workflow 구성과 이미지 게시 정책은 해당 작업에서 확정한다.

## 8. 운영 배포 및 CD 확장 계획

실제 운영 환경 구축과 배포 자동화는 프로젝트 핵심 기능 개발 이후 진행한다.

검토 대상은 다음과 같다.

- 배포 서버 및 실행 환경
- 운영 PostgreSQL 구성
- Docker Compose 기반 애플리케이션 실행
- 운영 환경변수 및 비밀값 관리
- 이미지 기반 배포 자동화
- 배포 후 애플리케이션 상태 검사
- 배포 실패 시 복구 및 롤백 전략

초기에는 단일 서버 기반의 단순한 배포 구성을 우선 검토한다.

운영 배포 방식은 실제 요구사항과 학습 범위를 기준으로 결정하며, 현재 단계에서 별도의 개발 서버나 Kubernetes 도입을 전제로 하지 않는다.

## 9. Jenkins 학습 범위

Jenkins는 GitHub Actions로 CI를 구축한 이후 기초 실습을 진행한다.

주요 학습 범위는 다음과 같다.

- Jenkins 실행 환경 구성
- Jenkins Pipeline 및 Jenkinsfile 이해
- GitHub 저장소 연동
- Gradle 빌드 및 테스트 자동화
- GitHub Actions와 Jenkins의 실행 및 관리 방식 비교

Jenkins와 GitHub Actions를 동시에 운영해야 하는 구조는 만들지 않는다.

## 10. 미확정 사항

다음 항목은 실제 구현 또는 후속 설계 과정에서 확정한다.

- CI Runner에서 사용할 Java 버전
- CI PostgreSQL 이미지 버전
- 기존 DB 초기화 스크립트의 CI 재사용 필요 여부
- CI 환경변수와 테스트 설정 연결 방식
- 필수 상태 검사 및 브랜치 보호 정책
- Docker 이미지 빌드와 게시 시점
- 운영 배포 대상과 배포 전략

결정이 확정되면 본 문서를 수정한다.

장기적으로 중요한 기술적 결정은 `docs/decisions/`에 ADR로 별도 기록한다.
