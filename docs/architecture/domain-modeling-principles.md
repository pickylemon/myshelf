# 제품 요구사항에서 출발하는 도메인 모델링

- **작성일:** 2026-10-29
- **관련 결정:** [ADR-011 — 사용자별 도서 메타데이터 스냅샷 저장](../decisions/011-user-book-metadata-snapshot.md)

## 1. 배경

MyShelf의 Feature 5를 설계하면서 공통 `Book` 엔티티를 도입할지 고민하게 되었다.

초기에는 개발자 관점에서 다음과 같은 기술적 문제를 중심으로 검토했다.

- 도서 메타데이터를 `UserBook`에 중복 저장해도 되는가?
- 정규화를 위해 `Book` 테이블을 분리해야 하는가?
- 공통 `Book`을 분리하면 JOIN 비용이 발생하지 않는가?
- 사용자 수가 증가했을 때 어떤 구조가 효율적인가?
- ISBN별 통계를 구현할 때 어느 모델이 유리한가?

모두 데이터 모델링에서 고려할 만한 문제다.

그러나 논의 과정에서 이러한 질문에 답하기 전에 **서비스 자체가 무엇을 제공하려는지 먼저 정의해야 한다는 점**을 발견했다.

이는 기술적으로 효율적인 데이터 모델을 찾는 문제와 비즈니스 요구사항에 적합한 도메인 모델을 설계하는 문제가 완전히 같지는 않다는 깨달음으로 이어졌다.

## 2. 제품의 목적이 도메인 모델에 미치는 영향

같은 도서 데이터를 사용하더라도 서비스의 목적에 따라 핵심 도메인은 달라질 수 있다.

### 2.1. Book 중심 서비스

도서 자체가 핵심 관리 대상인 서비스에서는 다음과 같은 기능이 중요할 수 있다.

- 공통 도서 상세정보 관리
- 도서별 리뷰 및 평점 집계
- 도서별 인기 순위와 추천
- 도서 메타데이터의 정합성 유지

이러한 서비스에서는 `Book`을 독립적인 도메인 개념으로 다루는 것이 자연스럽다.

여러 사용자의 활동은 특정 도서를 중심으로 연결된다.

### 2.2. UserBook 중심 서비스

반면 개인 독서 경험 관리 서비스에서는 다음과 같은 기능이 중요하다.

- 사용자가 관심 있는 도서 등록
- 개인 Shelf에 도서 분류
- 사용자별 독서 상태 관리
- 개인 서재 검색 및 정렬

여기서는 도서 자체보다 **사용자와 도서 사이의 관계**가 핵심이다.

같은 ISBN의 도서라도 사용자 A와 B에게 서로 다른 독서 상태와 관리 맥락을 갖는다.

### 2.3. MyShelf의 선택

MyShelf는 사용자의 독서 경험을 정리하고 관리하는 개인 서재 서비스로 정의한다.

따라서 현재 핵심 모델은 다음과 같다.

- `Shelf`: 사용자가 도서를 분류하고 관리하는 공간
- `UserBook`: 사용자가 등록하고 관리하는 도서
- `ShelfBook`: `UserBook`과 `Shelf`의 연결 및 Shelf 내 순서

공통 도서 카탈로그는 현재 핵심 도메인에 포함하지 않는다.

이는 `Book` 중심 모델이 잘못되었기 때문이 아니라, 현재 MyShelf가 해결하려는 문제에 `UserBook` 중심 모델이 더 적합하기 때문이다.

또한 두 모델은 배타적이지 않다. 서비스의 요구사항이 확장되면 공통 `Book`과 사용자별 `UserBook`이 함께 존재할 수 있다.

## 3. 데이터 모델링은 기술적 효율성만의 문제가 아니다

정규화, 저장 공간, JOIN 비용, 인덱스 등은 중요한 설계 요소다.

그러나 이러한 요소만으로 도메인 모델의 적절성을 판단할 수는 없다.

예를 들어 공통 `Book` 테이블은 동일 ISBN의 메타데이터 중복을 줄일 수 있다.

반면 공통 메타데이터가 수정되면 이를 참조하는 여러 사용자의 조회 결과가 함께 변경될 수 있다.

이 변경이 바람직한지는 데이터베이스만으로 판단할 수 없다.

- 최신 도서정보를 모든 사용자에게 제공하는 서비스라면 장점일 수 있다.
- 등록 당시의 도서정보를 독립적으로 유지하려는 서비스라면 의도하지 않은 변경일 수 있다.

따라서 데이터 모델을 결정할 때는 데이터의 중복 여부뿐 아니라 다음 사항을 함께 고려해야 한다.

1. 이 데이터는 서비스에서 무엇을 의미하는가?
2. 누가 이 데이터의 변경을 결정하는가?
3. 변경이 다른 사용자나 기능에 전파되어도 되는가?
4. 데이터의 최신성과 등록 당시 정보 중 무엇이 중요한가?
5. 현재 서비스가 실제로 요구하는 기능은 무엇인가?

MyShelf는 이 판단을 바탕으로 `UserBook`에 최소 메타데이터를 등록 시점의 스냅샷으로 저장하기로 결정했다.

구체적인 대안과 트레이드오프는 [ADR-011](../decisions/011-user-book-metadata-snapshot.md)에 기록한다.

## 4. 헥사고날 아키텍처와의 연결

도메인 모델을 결정하는 문제와 헥사고날 아키텍처를 적용하는 문제는 서로 다르지만 밀접하게 연결되어 있다.

### 4.1. 무엇을 중심에 둘 것인가

제품의 목적과 요구사항을 분석하여 핵심 도메인 개념과 규칙을 정의한다.

MyShelf에서는 사용자별 도서 관리가 중심이므로 `UserBook`, `Shelf` 및 그 관계를 모델링한다.

이는 도메인 모델링의 문제다.

### 4.2. 정의한 중심을 어떻게 보호할 것인가

헥사고날 아키텍처는 애플리케이션의 핵심 로직이 HTTP, JPA, 외부 API 같은 구체적인 기술에 불필요하게 의존하지 않도록 경계를 설계한다.

MyShelf에서는 다음과 같이 적용한다.

```text
              [Inbound Adapter]
                BookController
                      |
                      v
               [Inbound Port]
                      |
                      v
           [Application Service]
              /             \
             v               v
    [Outbound Port]     [Outbound Port]
           |                  |
           v                  v
   [External Adapter]  [Persistence Adapter]
           |                  |
           v                  v
       외부 도서 API       PostgreSQL
```

- Controller는 애플리케이션의 UseCase를 호출한다.
- Application Service는 도서 검색과 등록 정보 결합을 조율한다.
- 외부 API 호출과 영속성 처리는 Outbound Port를 통해 접근한다.
- 외부 API의 요청·응답 형식과 JPA 구현 세부사항은 Adapter에 격리한다.

이 구조는 MyShelf의 도메인 모델이 외부 기술의 변경에 불필요하게 영향받지 않도록 한다.

단, 헥사고날 아키텍처 자체가 `Book`과 `UserBook` 중 어느 모델을 선택해야 하는지 결정해 주는 것은 아니다.

핵심 도메인의 정의는 제품과 도메인 요구사항에 대한 판단이며, 헥사고날 아키텍처는 그 결과를 기술적으로 보호하는 설계 방식이다.

## 5. MyShelf에 적용할 설계 원칙

이번 경험을 바탕으로 다음 원칙을 유지한다.

### 5.1. 테이블보다 도메인 개념을 먼저 정의한다

데이터베이스 구조부터 설계하기보다 서비스가 다루는 개념과 규칙을 먼저 확인한다.

엔티티와 테이블은 그 개념을 표현하기 위한 수단이다.

### 5.2. 정규화와 성능은 요구사항 안에서 판단한다

정규화는 중요한 설계 원칙이지만 항상 최대한 분리하는 것이 정답은 아니다.

데이터 독립성, 변경 전파, 조회 특성, 운영 비용 등을 함께 고려한다.

성능이 실제 문제라면 예상에만 의존하지 않고 측정 결과를 근거로 판단한다.

### 5.3. 현재 요구사항에 필요한 만큼 모델링한다

미래에 사용할 가능성이 있다는 이유만으로 공통 도메인이나 복잡한 추상화를 미리 도입하지 않는다.

다만 향후 재검토할 조건과 현재 선택의 트레이드오프는 문서로 남긴다.

### 5.4. 외부 기술과 도메인의 경계를 구분한다

외부 API 응답 구조나 영속성 기술이 도메인 모델을 직접 결정하게 만들지 않는다.

Application 및 Domain 계층은 MyShelf의 요구사항을 기준으로 설계하고, 구체적인 기술과의 차이는 Adapter에서 처리한다.

## 6. 정리

이번 설계 과정에서 얻은 핵심 교훈은 다음과 같다.

**좋은 데이터 모델은 기술적인 효율성만으로 결정되지 않는다. 서비스가 해결하려는 문제와 제공하려는 가치를 이해하는 데서 출발한다.**

MyShelf에서는 먼저 사용자별 독서 경험 관리라는 제품의 목적을 확인했고, 이를 근거로 `UserBook` 중심 모델을 선택했다.

헥사고날 아키텍처는 이렇게 정의한 핵심 도메인과 애플리케이션 로직을 외부 기술로부터 분리하고 보호하기 위한 수단으로 활용한다.

기술적으로 가능한 설계는 여러 가지일 수 있다. 중요한 것은 현재 비즈니스 요구사항에 적합한 선택을 하고, 그 근거와 트레이드오프를 설명할 수 있는 것이다.
