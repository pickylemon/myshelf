# MyShelf CD 배포 방식 검토 및 선정

- 문서 유형: Planning / 기술 선택 기록
- 상태: SSM + S3 전환 코드 작성, 실제 배포 검증 전
- 대상 환경: GitHub Actions, GHCR, AWS EC2 (ARM64), Docker Compose, PostgreSQL, Redis

## 1. 현재 배포 방식과 변경 목표

전환 전 CD는 GitHub Actions에서 EC2에 파일을 복사한 뒤 배포 스크립트를 실행하는 방식이다. 현재 작업 파일에는 SSM + S3 전환 코드가 작성되어 있지만, 운영 적용 성공은 아직 검증하지 않았다.

```text
GitHub Actions
  ├─ SCP: Compose 파일과 배포 스크립트를 EC2에 복사
  └─ SSH: EC2의 deploy-ec2.sh 실행
             └─ GHCR 이미지 다운로드 → Compose 배포 → HTTP 응답 확인
```

이 과정에서 GitHub Actions는 SSH 개인 키를 사용한다. 또한 실행할 때마다 Runner의 IP에 대해 EC2의 SSH 포트(22번)를 임시로 열고, 작업 종료 시 접근 규칙을 삭제한다.

이번 변경은 **파일 전달을 S3로, 원격 명령 실행을 SSM Run Command로 교체**하는 것이다. 단일 EC2, Docker Compose, GHCR 및 기존 배포 스크립트는 계속 사용한다.

목표는 다음과 같다.

- CI/CD용 SSH 키와 임시 SSH 접근 규칙을 제거한다.
- 기존 GitHub OIDC 인증을 재사용하고, AWS IAM 권한으로 파일 전달과 명령 실행을 허용한다.
- CI가 검증한 커밋의 이미지와 배포 파일을 함께 사용한다.
- 기존 배포·HTTP 검증 로직을 최대한 재사용한다.

현재 SSH 기반 구현은 [CI/CD 아키텍처](../architecture/ci-cd.md)에 정리되어 있다. 이 문서는 앞으로 전환할 방식을 다룬다.

## 2. SSM과 S3는 각각 무엇을 담당하는가

| 구성 요소 | 이번 배포에서의 역할 |
|---|---|
| GitHub Actions | 배포할 커밋을 선택하고 파일을 준비한 뒤, EC2에 배포 명령을 요청한다. |
| S3 | Compose 파일과 배포 스크립트를 보관한다. EC2는 배포할 버전의 파일을 내려받는다. |
| SSM Run Command | EC2에 설치된 SSM Agent를 통해 셸 명령을 실행한다. SSH 접속을 대신한다. |
| GHCR | Docker 이미지를 보관한다. EC2는 배포할 버전의 이미지를 내려받는다. |
| OIDC / IAM | GitHub Actions가 AWS 임시 자격 증명을 발급받고, 허용된 AWS 작업을 수행하게 한다. |

SSM으로 명령만 실행하고 EC2에 있는 기존 파일을 그대로 사용하면, Git에서 Compose 파일이나 스크립트를 수정해도 EC2에는 반영되지 않을 수 있다. 따라서 **명령 실행 경로와 함께 배포 파일을 갱신하는 경로도 필요하다.**

이번에는 필요한 파일을 `deploy.tar.gz` 하나로 압축하여 S3에 올리고, EC2가 내려받도록 한다. 이 압축 파일을 이하 **배포 파일 묶음**이라고 부른다. AWS도 S3에서 파일을 내려받아 Systems Manager로 실행하는 구성을 제공한다. [AWS 공식 문서](https://docs.aws.amazon.com/systems-manager/latest/userguide/integration-s3.html)

## 3. 대안 비교와 결정

| 방식 | 배포 방법 | 이번 판단 |
|---|---|---|
| 기존 SSH + SCP | GitHub-hosted Runner에서 파일 복사 후 SSH로 스크립트 실행 | 구현되어 있지만 SSH 키와 임시 접근 규칙이 계속 필요하다. |
| 자체 호스팅 Runner + SSH/SCP | 별도 Runner 서버에서 운영 EC2에 파일 복사·명령 실행 | 사설망 접근과 기존 배포 로직 재사용이 가능하지만, Runner 서버 운영과 SSH 키 관리가 추가된다. |
| 운영 EC2에 Runner 설치 | 운영 EC2의 Runner가 배포 파일을 준비하고 로컬 스크립트 실행 | SSH/SCP 없이 실행할 수 있지만, 워크플로 실행 환경과 운영 서비스가 같은 서버를 공유한다. |
| SSM으로 실행만 교체 | SSM으로 EC2의 기존 스크립트 실행 | 변경은 작지만, 최신 배포 파일을 전달할 방법이 별도로 필요하다. |
| **SSM + S3 (선택)** | S3에서 파일 다운로드 후 SSM으로 배포 실행 | SSH를 제거하면서 기존 EC2·Compose 배포 구조를 유지할 수 있다. |
| AWS CodeDeploy | 파일 배치와 단계별 실행을 전용 서비스로 관리 | AppSpec 파일, 배포 그룹, 에이전트 등 새로운 구성이 필요하므로 후속 학습 후보로 둔다. |
| Amazon ECS | ECS 서비스가 컨테이너 실행·교체를 관리 | 현재 Compose 중심의 운영 구조를 크게 바꿔야 하므로 이번 범위에서 제외한다. |

선정한 구성은 **SSM Run Command + S3 배포 파일 묶음 + GHCR 이미지**다.

SSM으로 EC2에 명령을 실행하면서 기존 배포 스크립트를 활용할 수 있고, S3에 커밋별 파일을 보관하여 이미지와 배포 설정의 버전을 맞출 수 있다. 이번에는 배포 전달·실행 방법을 바꾸는 데 집중한다.

CodeDeploy는 파일 배치·실행 시점 등을 AppSpec으로 정의하는 배포 서비스이고, ECS는 컨테이너 실행과 유지 자체를 관리하는 서비스다. 배포 대상이나 운영 요구가 늘어나면 다시 검토한다. [CodeDeploy 공식 문서](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployment-steps-server.html), [ECS 공식 문서](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-configuration.html)

### 자체 호스팅 Runner를 선택하지 않은 이유

Runner의 호스팅 방식은 **워크플로를 어디에서 실행할지**에 관한 선택이고, SSH와 SSM은 **운영 EC2에 명령을 어떻게 전달할지**에 관한 선택이다. 자체 호스팅 Runner에서도 SSH 또는 SSM을 사용할 수 있다.

별도 Runner 서버를 운영 EC2와 같은 VPC에 두면 사설 IP로 SSH/SCP를 사용할 수 있다. 운영 EC2의 SSH 접근을 Runner에서만 허용하면, 기존의 Runner IP 확인·임시 보안 그룹 변경 로직을 제거하면서 배포 스크립트를 재사용할 수 있다. 다만 SSH 키는 계속 필요하고, Runner 서버의 비용·OS 관리·장애 대응도 맡아야 한다.

운영 EC2 자체에 Runner를 설치하면 로컬에서 배포할 수 있으므로 SSH/SCP가 필요하지 않다. 해당 커밋을 체크아웃하여 배포 파일을 준비하는 구조라면 S3 전달도 생략할 수 있다. 대신 워크플로의 실행 권한이 운영 서버에 직접 영향을 주며, 같은 서버에서 테스트·이미지 빌드까지 수행하면 서비스와 CPU·메모리를 경쟁한다. GitHub도 자체 호스팅 Runner의 실행 코드와 접근 권한을 신중히 관리하도록 안내한다. [GitHub 보안 문서](https://docs.github.com/en/actions/reference/security/secure-use)

현재 MyShelf는 단일 운영 EC2를 사용하며, 별도 Runner 운영이 필요한 요구사항은 없다. 따라서 **GitHub-hosted Runner를 유지하고 SSM + S3로 전환**한다. 사설망 전용 접근이나 전용 빌드 환경이 필요해지면 자체 호스팅을 다시 검토한다. SSH 자체가 부적절해서 제외한 것은 아니다.

## 4. 어떤 파일을 어디에 보관하는가

배포 파일의 원본과 변경 이력은 Git에서 관리한다. S3는 특정 커밋의 검증된 배포 파일을 EC2에 전달하는 **아티팩트 저장소**로 사용한다. 여기서 아티팩트는 배포를 위해 준비한 파일 묶음을 뜻한다.

**매 배포마다 파일의 변경 여부와 관계없이, 이미지와 동일 커밋의 다섯 파일을 하나로 묶어 S3에 업로드하고 EC2에 적용한다.**

| 대상 | 보관 위치 | EC2에서 사용하는 방법 |
|---|---|---|
| 애플리케이션 이미지 | GHCR의 `sha-<커밋-SHA>` 태그 | Docker로 다운로드한다. |
| `compose.yaml` | Git → S3 배포 파일 묶음 | 내려받아 운영 배포에 적용한다. |
| `compose.prod.yaml` | Git → S3 배포 파일 묶음 | 내려받아 운영 배포에 적용한다. |
| `scripts/deploy-ec2.sh` | Git → S3 배포 파일 묶음 | 내려받아 EC2에서 실행한다. |
| `scripts/prepare-release-ec2.sh` | Git → S3 배포 파일 묶음 | 다운로드한 압축 파일을 검증하고 릴리스 디렉터리를 준비한다. |
| `scripts/activate-release-ec2.sh` | Git → S3 배포 파일 묶음 | `current`를 전환하고 배포 스크립트를 호출한다. |
| 운영 환경변수와 비밀정보 | EC2의 `/opt/myshelf/.env` | 기존 파일을 유지하며, 배포 파일 묶음에는 포함하지 않는다. |

예를 들어 배포할 커밋의 전체 SHA가 `<SHA>`라면 다음 두 대상을 함께 사용한다.

```text
GHCR 이미지: ghcr.io/pickylemon/myshelf:sha-<SHA>
S3 객체 키: releases/<SHA>/deploy.tar.gz
```

SHA는 Git 커밋을 식별하는 값이며, 여기서는 40자리 전체 값을 사용한다. S3 객체 키에는 SHA를 포함한다. 위 경로는 예시이며, 구체적인 키 구조는 구현 단계에서 확정한다.

같은 SHA의 이미지와 파일 묶음은 덮어쓰지 않는 것을 원칙으로 한다. 다만 **이름에 SHA를 넣는 것만으로 덮어쓰기가 차단되지는 않는다.**

### 동일 커밋의 CI를 재실행하는 경우

동일 SHA의 S3 아티팩트가 이미 존재하면 **배포 대상 파일의 경로와 내용을 비교하여, 같으면 기존 아티팩트를 재사용하고 다르면 CI를 실패 처리한다.** 매 배포마다 해당 커밋의 파일을 게시한다는 정책에서, 동일 커밋 재실행 시에는 같은 내용을 다시 덮어쓰지 않는다.

정책의 비교 대상은 배포 파일이다. 현재 CI 구현은 파일 순서·소유자·mtime과 gzip 헤더를 고정하여 압축 파일을 재현 가능하게 만들고, 기존 압축 파일과 SHA-256을 비교한다. 파일이 같은 경우에도 체크섬이 달라지지 않는지는 실제 CI 재실행으로 검증한다. EC2에서는 압축 해제한 다섯 파일의 내용을 직접 비교한다.

GHCR에 동일 SHA의 이미지가 있으면 AMD64·ARM64 구성이 모두 존재하는지 확인하고 재사용한다. 이미지가 명시적으로 없을 때만 빌드·게시하며, 인증·통신 오류나 아키텍처 누락은 실패로 처리한다. 같은 SHA의 이미지 게시 작업은 순차 실행한다. 이는 이 워크플로의 덮어쓰기를 방지하는 정책이며, 외부에서 태그를 변경하는 것까지 차단하지는 않는다. S3 파일이 같다는 사실만으로 이미지까지 동일하다고 판단하지 않는다.

운영 `.env`를 유지한다는 것은 비밀번호 등 기존 설정을 보존한다는 의미다. 기존 배포 스크립트가 수행하는 `MYSHELF_IMAGE` 값 변경은 계속 필요하다.

### Git으로 관리하는 파일을 매번 S3에 올리는 이유

Compose 파일과 배포 스크립트는 매 배포마다 변경되지는 않는다. 그럼에도 매번 전달하는 이유는 다음과 같다.

- 이미지와 실제 적용되는 배포 파일을 같은 커밋 기준으로 맞춘다.
- EC2에 이전 파일이 남아 발생하는 설정 불일치를 방지한다.
- 파일 변경 여부를 비교하거나 마지막 업로드·적용 버전을 별도로 추적하는 로직을 줄인다.
- 파일 크기가 작아 매번 전달하는 비용·성능 부담이 제한적이라고 판단했다. S3 비용이 발생할 가능성은 별도로 고려한다.
- 특정 커밋의 이미지와 배포 파일을 함께 선택하여 당시 배포 구성을 재현하기 쉽게 한다.

Git은 원본과 변경 이력을 관리하고, S3는 배포할 파일을 전달한다. 두 저장소의 역할을 구분한다.

### 검토했지만 선택하지 않은 파일 전달 방식

| 방식 | 선택하지 않은 이유 |
|---|---|
| EC2에 한 번 배치한 파일을 계속 재사용 | 단순하지만 Git의 배포 설정과 EC2의 실제 파일이 달라질 수 있다. |
| 파일이 변경되었을 때만 S3 업로드 | 전송은 줄지만 마지막 업로드 버전과 EC2 적용 버전을 관리하는 로직이 필요하다. |
| SSM 명령에 파일 내용을 직접 포함 | 별도 저장소는 필요 없지만 파일 전달·인코딩·크기 제한 등의 처리를 직접 구현해야 한다. |

현재는 전송량을 줄이는 것보다 구성의 복잡도를 줄이고 배포 재현성을 확보하는 것을 우선한다.

## 5. 전환 후 배포 순서

1. `main` Push를 계기로 GitHub Actions CI가 실행되어 해당 커밋을 테스트한다.
2. 검증된 커밋의 `sha-<커밋-SHA>` 이미지가 있으면 재사용하고, 없으면 AMD64·ARM64 이미지를 빌드하여 GHCR에 게시한다.
3. CI는 GitHub OIDC로 AWS 임시 자격 증명을 발급받고, 같은 커밋의 Compose 파일과 배포 스크립트를 압축하여 S3에 올린다.
4. **이미지 게시와 S3 업로드가 모두 성공하여 CI가 성공한 경우에만 CD를 진행한다.** CD는 해당 CI의 커밋 SHA를 배포 기준으로 사용한다.
5. CD는 GitHub OIDC로 AWS 인증을 수행한 뒤, SSM Run Command로 대상 EC2에 배포 명령과 SHA를 전달한다.
6. EC2는 배포 잠금을 획득하고 아티팩트를 임시 경로로 다운로드한다. `prepare-release-ec2.sh`가 전체 파일과 설정을 검증하여 `releases/<SHA>`를 준비한다.
7. `activate-release-ec2.sh`가 `current` 심볼릭 링크를 한 번에 전환한 뒤 `deploy-ec2.sh`를 호출한다. 배포 스크립트는 동일 SHA의 이미지를 내려받고 Docker Compose로 애플리케이션을 갱신한다. CD에서 배포 스크립트를 중복 호출하지 않는다.
8. 기존 실행 이미지·HTTP 응답 확인과 배포 이력 기록을 유지한다.
9. GitHub Actions는 SSM 명령이 끝날 때까지 기다린 뒤, 원격 실행 결과를 CD 성공·실패에 반영한다.

`SendCommand`가 성공했다는 것은 **명령 요청이 접수되었다는 의미**다. EC2의 배포 작업까지 성공했다는 의미는 아니므로 9번 단계가 필요하다.

현재 저장소에는 [SSM 연결 확인용 워크플로](../../.github/workflows/ssm-smoke-test.yaml)가 있다. 이 워크플로는 간단한 명령을 보내고 종료 결과를 확인한다. 사전 실습에서는 SSM Agent, EC2용 IAM Role, GitHub Actions OIDC 및 SSM Run Command 연동을 검증했다. **S3 게시부터 실제 배포까지 이어지는 전환 코드는 작성 중이며, 전체 운영 흐름은 아직 검증 전이다.**

### 최초 운영 파일 이관

새 CD를 적용하기 전에 `bootstrap-release-ec2.sh`로 기존 운영 파일 세 개를 최초 릴리스로 복사하고 `current` 링크를 만든다. 실행 이미지와 `.env`의 이미지 태그가 일치하는지 확인하며, 컨테이너·데이터 볼륨·`.env`는 변경하지 않는다.

이관 중 링크 생성이 실패해도 기존 릴리스의 파일이 같으면 재실행할 수 있다. `current`가 다른 릴리스를 가리키거나 파일 내용이 다르면 중단한다. 이관도 CD와 같은 배포 잠금을 사용한다.

최초 릴리스는 EC2에 있던 파일의 스냅샷이다. 같은 SHA의 Git 파일과 일치한다고 간주하지 않는다. 준비·활성화 스크립트가 없는 기존 세 파일 릴리스는 복구용 예외이며, 이후 새 릴리스는 다섯 파일을 모두 포함한다.

## 6. 구현할 때 확인할 사항

### 권한과 인증

- GitHub Actions의 IAM Role에는 지정한 S3 경로의 파일 업로드 권한과 대상 EC2의 SSM 명령 실행·결과 조회 권한을 부여한다.
- EC2의 IAM Role에는 SSM 이용 권한과 지정한 S3 파일을 읽을 권한을 부여한다. 실제 다운로드 방식에 필요한 권한만 추가한다.
- S3 버킷의 공개 접근을 차단한다. `.env`, 비밀번호, 토큰을 압축 파일이나 SSM 명령·로그에 넣지 않는다.
- AWS IAM 권한과 GHCR 인증은 별개다. 비공개 GHCR 이미지를 내려받는 기존 Docker 인증도 유지해야 한다.

### 파일 적용과 실행 환경

- SSM Agent가 실행 중이고 EC2에서 필요한 AWS 서비스에 통신할 수 있어야 한다.
- 운영 상태 파일은 `/opt/myshelf`에 유지하고, 배포 파일은 `/opt/myshelf/releases/<SHA>`에 둔다. `current`는 현재 사용하는 릴리스 디렉터리를 가리킨다.
- 같은 SHA의 전체 파일을 검증·준비한 뒤 임시 심볼릭 링크의 rename으로 `current`를 한 번에 전환한다. 파일을 하나씩 덮어쓰다가 서로 다른 버전이 섞이지 않도록 한다.
- 다운로드·검증·파일 집합 전환에 실패하면 배포를 중단하고, 기존 파일 집합을 계속 참조할 수 있도록 한다. 이 원칙은 파일 버전 혼재를 방지하기 위한 것이며, 애플리케이션이나 DB의 자동 롤백을 의미하지 않는다.
- Linux의 SSM Run Command는 기본적으로 root 권한으로 실행되므로 파일 소유권과 Docker 인증 위치를 확인한다.
- 운영 `.env`의 위치와 기존 Compose 프로젝트 식별자·데이터 볼륨을 유지한다. 릴리스 디렉터리가 달라져도 다른 프로젝트로 컨테이너를 생성하지 않도록 한다.

### 실패 처리와 운영 범위

- S3 업로드 실패는 CI 실패로 처리한다. 이미지 게시 또는 S3 업로드 중 하나라도 실패하면 CD가 실행되지 않아야 한다.
- 기존 CD의 동시 실행 제한을 유지하고, 늦게 끝난 CI 때문에 오래된 커밋이 배포되지 않도록 배포 순서도 검토한다.
- SSM 명령 실패와 대기 시간 초과를 GitHub Actions의 실패로 처리한다. 기존 HTTP 확인도 계속 수행한다.
- 후속 구현에서는 자동 복구 시도를 포함하도록 범위가 확대되었다. 활성화 이후 배포가 실패하면 이전 링크와 `.env`를 복원하고 기존 이미지로 Compose를 재적용한 뒤 HTTP 응답을 확인한다. 복구에 성공해도 해당 신규 배포의 CD 결과는 실패로 유지한다.
- 복구 실패 시 `.env` 백업을 보존하고 수동 조치에 사용할 경로를 출력한다. 자동 복구의 성공을 보장하거나 DB 마이그레이션을 되돌리는 기능은 아니다. 이전 애플리케이션과 변경된 DB 스키마의 호환성이 필요하며, 강제 종료·실행 시간 제한에 의해 복구가 완료되지 않을 수도 있다.
- S3 저장 용량과 요청 등에 비용이 발생할 수 있으므로 배포 파일의 보존 기간을 정한다.

## 7. 전환 완료 기준

- [ ] 파일 변경 여부와 관계없이 매 배포마다 동일 커밋의 다섯 배포 파일을 묶어 S3에 게시한다.
- [ ] 동일 SHA의 GHCR 이미지가 있으면 AMD64·ARM64 구성을 검증하여 재사용하고 덮어쓰지 않는다.
- [ ] GHCR 이미지 게시와 S3 업로드가 모두 성공한 경우에만 CD가 실행된다.
- [ ] S3 업로드 실패 시 CI가 실패하고 CD가 실행되지 않는 것을 검증한다.
- [ ] 동일 SHA 재실행 시 기존 S3 아티팩트의 파일 경로·내용이 같으면 재사용하고, 다르면 CI가 실패한다.
- [ ] EC2가 같은 SHA의 파일을 내려받아 검증·적용한다.
- [ ] 전체 파일을 검증한 뒤 참조 대상을 한 번에 전환하여 서로 다른 버전의 파일이 섞이지 않는다.
- [ ] 파일 다운로드·검증·전환 실패 시 배포가 중단되고 기존 파일 집합을 계속 참조할 수 있다.
- [ ] SSM을 통해 배포 스크립트가 실행되고, GitHub Actions가 실제 종료 결과를 확인한다.
- [ ] EC2에서 해당 SHA의 GHCR ARM64 이미지가 실행된다.
- [ ] Compose 상태·실행 이미지·HTTP 응답을 확인하고 배포 이력을 기록한다.
- [ ] 운영 `.env`의 비밀정보와 기존 PostgreSQL·Redis 데이터가 의도치 않게 삭제·초기화되지 않는다.
- [ ] 최초 이관 중 실패 후 동일 파일로 재실행할 수 있고, 운영 컨테이너·볼륨·`.env`가 유지된다.
- [ ] 배포 실패 시 이전 릴리스 복구를 시도하며, 복구 실패 시 백업을 보존한다. DB 호환성이 유지되는 조건에서 검증한다.
- [ ] SSH/SCP 없이 전체 배포가 성공한다.
- [ ] 전환 검증 후 CI/CD용 SSH 키와 임시 보안 그룹 변경 로직·불필요한 IAM 권한을 정리한다.
