# Feature 4 — 도서 및 Shelf 관리 기능 정의

> 상태: Draft · 주요 기능 및 일부 정책 확정  
> 범위: 도서 탐색, 독서 상태 관리, Shelf 구성  
> 상위 문서: [MyShelf 서비스 기획 개요](./myshelf-product-overview.md)

## 1. 목표

MyShelf는 독서와 필사를 통해 개인의 취향을 아카이빙하는 서비스다.

Feature 4에서는 사용자가 관심 있는 책을 발견하고, 자신의 독서 상태를 관리하며, 여러 Shelf에 자유롭게 책을 구성하는 경험을 구현한다.

Shelf는 실제로 소유한 책을 보관하는 물리적인 책장이 아니라, **읽었거나 읽고 싶은 책을 자신의 기준으로 모으고 배치하는 디지털 보드**다.

이번 Feature의 목표는 다음과 같다.

- 외부 도서정보를 활용하여 책을 검색한다.
- 관심 있는 책을 Shelf에 등록한다.
- 사용자별 독서 상태를 관리한다.
- 사용자가 여러 Shelf를 생성하고 자유롭게 구성한다.
- 동일한 책을 여러 Shelf에 배치할 수 있다.
- 다른 사용자의 도서 및 Shelf 데이터에 접근하지 못하도록 한다.

## 2. 기능 요구사항

### 2.1. 도서 탐색 및 조회

| 기능 | 설명 |
|---|---|
| 도서 검색 | 제목, 저자 등으로 도서를 검색한다. |
| 도서 상세 조회 | 제목, 저자, 표지, 출판사, ISBN 등 도서정보를 확인한다. |
| 전체 도서 조회 | 사용자의 모든 Shelf에 속한 책을 중복 없이 조회한다. |

도서정보는 외부 도서 API를 활용한다. 전자책 본문 등 도서 콘텐츠는 제공하지 않는다.

책을 별도의 개인 도서 목록에 먼저 등록하는 단계는 두지 않는다. **특정 Shelf에 책을 추가하는 행위가 곧 사용자의 도서 등록이다.**

### 2.2. 독서 상태 관리

사용자별로 다음 세 가지 상태를 관리한다.

| 상태 | 의미 |
|---|---|
| `WANT_TO_READ` | 앞으로 읽고 싶은 책 |
| `READING` | 현재 읽고 있는 책 |
| `READ` | 완독한 책 |

- 사용자는 Shelf에 등록한 책의 독서 상태를 변경할 수 있다.
- 독서 상태는 개별 Shelf가 아닌 사용자와 책의 관계에 속한다.
- 같은 책이 여러 Shelf에 존재하더라도 독서 상태는 동일하다.
- 실물 도서의 소장 여부는 관리하지 않는다.
- 페이지 단위 진행률이나 독서량은 관리하지 않는다.

### 2.3. Shelf 관리

Shelf는 사용자가 원하는 기준으로 책을 모으는 독립적인 보드다.

| 기능 | 설명 |
|---|---|
| Shelf 생성 | 새로운 Shelf를 생성한다. |
| Shelf 조회 | 자신의 Shelf 목록과 각 Shelf에 속한 책을 조회한다. |
| Shelf 수정 | Shelf의 이름 등 기본 정보를 변경한다. |
| Shelf 삭제 | 더 이상 사용하지 않는 Shelf를 삭제한다. |
| 책 추가 | 특정 Shelf에 책을 추가한다. |
| 책 제거 | 특정 Shelf에서 책을 제거한다. |
| 책 순서 변경 | Shelf에 배치된 책의 순서를 사용자가 직접 변경한다. |

## 3. 확정된 비즈니스 정책

### 3.1. 도서와 Shelf의 관계

- 사용자는 여러 Shelf를 생성할 수 있다.
- 하나의 책은 여러 Shelf에 동시에 속할 수 있다.
- 사용자가 관리하는 책은 하나 이상의 Shelf에 속한다.
- 책을 처음 Shelf에 추가하면 사용자의 관리 대상이 된다.
- 동일한 책의 독서 상태는 어느 Shelf에서 조회하더라도 동일하다.
- Shelf별 책의 배치 순서는 독립적으로 관리한다.
- 특정 Shelf에서 책을 제거해도 다른 Shelf에 속한 동일한 책에는 영향을 주지 않는다.
- 마지막 Shelf에서 책이 제거되면 사용자의 전체 도서 조회 결과에서도 제외된다.

마지막 Shelf에서 제거한 책의 독서 상태 및 연관 기록을 실제로 삭제할지 보존할지는 별도로 결정한다.

### 3.2. 전체 도서 목록

전체 도서 목록은 **사용자의 모든 Shelf에 속한 책을 중복 없이 조회하는 논리적인 범위**다.

이를 위한 별도의 전체 도서 Shelf 엔티티를 생성하지 않는다.

외부 도서 검색 결과에 등장한 책은 사용자가 Shelf에 추가하기 전까지 자신의 관리 대상에 포함되지 않는다.

### 3.3. 도서 제거

- 사용자는 개별 Shelf에서 책을 제거할 수 있다.
- MyShelf 전체에서 책을 일괄 제거하는 별도 기능은 제공하지 않는다.
- 어떤 책이 모든 Shelf에서 제거되면 전체 도서 목록에서도 나타나지 않는다.
- 마지막 Shelf에서 책을 제거할 때의 내부 데이터 처리 정책은 추후 결정한다.

### 3.4. 사용자별 데이터 격리

- 사용자는 자신의 도서 관리 정보와 Shelf만 관리할 수 있다.
- 다른 사용자의 독서 상태, Shelf 구성 및 배치 순서를 조회하거나 변경할 수 없다.
- 도서 자체의 메타데이터와 사용자별 관리 정보는 개념적으로 구분한다.

## 4. 핵심 사용자 시나리오

1. 사용자가 로그인한 뒤 도서를 검색한다.
2. 관심 있는 책을 발견하면 등록할 Shelf를 선택하거나 새 Shelf를 생성한다.
3. 선택한 Shelf에 책을 추가하면 해당 책이 자신의 관리 대상이 된다.
4. 필요하다면 동일한 책을 다른 Shelf에도 추가한다.
5. 각 Shelf 안에서 책의 순서를 원하는 대로 조정한다.
6. 책을 읽기 시작하거나 완독하면 독서 상태를 변경한다.
7. 상태 변경 결과는 해당 책이 속한 모든 Shelf에 동일하게 반영된다.
8. 특정 Shelf에서 책을 제거해도 다른 Shelf에 속한 동일한 책은 유지된다.
9. 모든 Shelf에서 제거한 책은 전체 도서 목록에서도 제외된다.

위 시나리오는 대표적인 사용 흐름이며, 사용자가 반드시 이 순서를 따라야 한다는 의미는 아니다.

## 5. 미결정 정책

다음 사항은 구현 전에 추가 논의한다.

| 주제 | 논의 사항 |
|---|---|
| 도서 중복 | 동일한 책의 판본·ISBN 차이를 어떻게 판단할 것인가? |
| 도서 등록 | 최초 등록 시 독서 상태는 기본값으로 지정할지, 사용자가 선택할지? |
| 최초 Shelf 생성 | Shelf가 하나도 없는 사용자의 첫 도서 등록 경험을 어떻게 구성할 것인가? |
| 상태 변경 | 독서 상태 간 이동을 자유롭게 허용할 것인가? |
| 독서 날짜 | 독서 시작일·완독일을 기록할 것인가? |
| 마지막 Shelf에서 제거 | 기존 독서 상태 및 연관 기록을 삭제할지 보존할지? |
| Shelf 삭제 | 해당 Shelf에만 존재하는 책과 관련 기록을 어떻게 처리할 것인가? |
| 검색·정렬 | 검색, 필터, 정렬, 페이지네이션의 초기 범위 |
| 도서정보 | 외부 API에서 검색되지 않는 책의 등록 방법 |

확정되지 않은 정책을 구현 편의에 따라 임의로 결정하지 않는다.

## 6. 완료 기준

다음 사항을 구현 및 테스트로 검증할 수 있으면 Feature 4의 핵심 기능이 완료된 것으로 판단한다.

- 사용자가 외부 도서정보를 검색하고 특정 Shelf에 책을 등록할 수 있다.
- 여러 Shelf를 생성·조회·수정·삭제할 수 있다.
- 동일한 책을 여러 Shelf에 등록할 수 있다.
- 전체 도서 목록은 모든 Shelf의 책을 중복 없이 보여준다.
- 등록한 도서의 정보 및 독서 상태를 조회·변경할 수 있다.
- 같은 책의 독서 상태 변경이 모든 Shelf에 동일하게 반영된다.
- Shelf별로 책의 배치 순서를 독립적으로 변경할 수 있다.
- 한 Shelf에서 책을 제거해도 다른 Shelf에 속한 동일한 책에는 영향을 주지 않는다.
- 모든 Shelf에서 제거된 책은 전체 도서 목록에 나타나지 않는다.
- 다른 사용자의 도서 및 Shelf 데이터에 접근하거나 이를 변경할 수 없다.
- 추가 합의한 중복 등록·삭제·상태 변경 정책을 테스트로 검증한다.

## 7. 이번 Feature의 제외 범위

다음 기능은 전체 서비스 기획에 포함되지만 Feature 4에서는 구현하지 않는다.

- 문장 수집 및 필사
- Paper 관리
- Collection 관리
- AI 도서 큐레이션
- 독서 진행률 및 상세 독서 통계
- Shelf 공개·공유 및 소셜 기능
- Redis·Kafka 등 별도 인프라를 활용한 고급 기능

후속 확장 가능성은 고려하되, 현재 요구사항에 필요하지 않은 구조를 선제적으로 도입하지 않는다.
