# Feature 4 — 개인 서재 관리 기능 기획

> 상태: Draft · 킥오프 논의용 초안  
> 범위: MyShelf의 개인 서재 및 독서 활동 관리  
> 관련 작업: Feature 4 — 개인 서재 및 독서 상태 관리  
> 이 문서는 **사용자 관점의 요구사항과 정책을 합의하기 위한 문서**다. 확정되지 않은 사항은 결정된 것처럼 취급하지 않는다.

## 1. 기획 배경과 목표

MyShelf는 사용자 인증과 JWT 기반 API 요청 인증을 마련했다. Feature 4에서는 이를 실제 사용자 데이터와 연결하여, 로그인한 사용자가 **자신의 책과 독서 상태를 관리하는 경험**을 구현한다.

이번 Feature의 목표는 다음과 같다.

- 사용자가 자신의 서재에 책을 등록하고 조회·수정·삭제할 수 있다.
- 사용자별 독서 상태를 기록하고 변경할 수 있다.
- 다른 사용자의 서재 데이터는 조회하거나 변경할 수 없다.
- 추후 독서 통계 및 AI 서재 비서가 활용할 수 있는 일관된 데이터를 축적한다.

> **논의 필요:** MyShelf의 핵심 가치는 **도서 컬렉션 관리**, **독서 활동 관리**, 또는 **두 기능의 결합** 중 무엇인가?

## 2. 핵심 사용자 시나리오 (초안)

1. 사용자는 로그인한 뒤 자신의 서재를 연다.
2. 관심 있는 책을 서재에 등록하고 '읽고 싶음' 상태로 관리한다.
3. 책을 읽기 시작하면 독서 상태를 '읽는 중'으로 변경한다.
4. 완독하면 상태를 '완독'으로 변경한다.
5. 자신의 서재에서 책을 찾아 상세 정보와 독서 상태를 확인한다.
6. 더 이상 관리하지 않을 책은 서재에서 제거한다.

위 흐름은 **대표 사용 사례**이지, 상태 전이를 반드시 이 순서로만 강제한다는 뜻은 아니다.

## 3. 기능 후보 및 MVP 범위

| 기능 | 제안 우선순위 | 결정 상태 | 비고 |
|---|---|---|---|
| 내 서재에 책 등록 | 필수 | 논의 중 | 직접 입력 vs 외부 도서 검색 결정 필요 |
| 내 서재 책 목록 조회 | 필수 | 논의 중 | 초기 검색·정렬·페이징 범위 결정 필요 |
| 내 서재 책 상세 조회 | 필수 | 논의 중 | 최소 제공 항목 합의 필요 |
| 독서 상태 변경 | 필수 | 논의 중 | 상태 전이 및 날짜 처리 정책 결정 필요 |
| 내 서재에서 책 제거 | 필수 | 논의 중 | 삭제의 의미·이력 보존 여부 결정 필요 |
| 사용자별 데이터 접근 제한 | 필수 | 논의 중 | 자기 서재만 조회·수정하도록 제한 |
| 독서 메모·평점 | 선택 | 보류 | MVP 범위 확정 때 재검토 |
| 외부 도서 검색 API | 선택 | 보류 | 초기 등록 방식 결정과 연결 |
| 독서 통계·AI 추천 | 후속 Feature | 제외 제안 | 기반 데이터만 고려 |
| Redis·Kafka·AI Agent | 후속 Feature | 제외 제안 | Feature 4의 기능 완성에 집중 |

**MVP 제안:** 등록 → 목록/상세 조회 → 상태 변경 → 삭제 → 사용자별 접근 제한까지 먼저 완성한다. 위 범위는 킥오프에서 확정한다.

## 4. 비즈니스 정책 — 킥오프 결정 필요

| 논의 주제 | 질문 | 현재 상태 |
|---|---|---|
| 서비스의 중심 가치 | 소장 목록 중심인가, 독서 과정 기록 중심인가? | 미결정 |
| 책 등록 방식 | 제목·저자 등을 직접 입력하는가, 외부 API로 검색하는가? | 미결정 |
| 중복 등록 | 한 사용자가 같은 책을 여러 번 등록할 수 있는가? 무엇을 같은 책으로 볼 것인가? | 미결정 |
| 독서 상태 | `WANT_TO_READ`, `READING`, `FINISHED`로 충분한가? | 후보 |
| 상태 전이 | '읽고 싶음'에서 바로 '완독' 가능한가? 완독 후 다시 읽을 수 있는가? | 미결정 |
| 날짜와 독서 이력 | 시작일·완독일을 자동 기록할까? 상태를 되돌리면 어떻게 할까? | 미결정 |
| 삭제 정책 | 서재에서 제거하면 기록도 삭제할까? 복구가 필요한가? | 미결정 |
| 소유권 위반 | 다른 사용자의 책 ID로 접근했을 때 어떤 동작을 보여줄까? | 미결정 |
| 검색과 목록 | 제목 검색, 상태별 필터, 정렬, 페이징 중 어디까지 제공할까? | 미결정 |

> 정책을 정한 다음 도메인 모델과 DB 제약조건을 설계한다. 지금은 특정 구현 방식을 전제하지 않는다.

## 5. 도메인 설계 전에 합의할 사항

현재 `Book`과 `ShelfBook`의 분리 여부는 확정하지 않는다.

- **책 자체의 정보:** 제목, 저자, ISBN 등 여러 사용자가 공유할 수 있는 정보
- **사용자별 정보:** 누가 서재에 등록했는지, 어떤 독서 상태인지, 언제 완독했는지 등

동일한 책을 여러 사람이 등록하는 경우, 중복 판단 기준, 향후 외부 도서 검색 필요성을 먼저 결정한 뒤 두 개의 모델로 분리할지 판단한다.

## 6. 완료 기준 초안 (사용자 관점)

다음 상황을 구현·테스트로 확인할 수 있으면 Feature 4의 핵심 사용자 경험을 제공했다고 판단한다.

- 로그인한 사용자가 책을 등록하고 자신의 목록과 상세 화면에서 확인한다.
- 등록한 책의 독서 상태를 변경하면 이후 조회에도 변경 결과가 반영된다.
- 서재에서 책을 제거하면 자신의 목록에서 더 이상 나타나지 않는다.
- 서로 다른 두 사용자의 서재 데이터가 섞이지 않는다.
- 사용자 A가 사용자 B의 책을 조회·변경·삭제하려는 시도는 허용되지 않는다.
- 합의한 중복 등록 및 상태 변경 정책을 테스트로 검증한다.

> 실제 API 경로, HTTP 상태 코드, 테이블 이름, Java 클래스 구조 등은 기획 합의 후 설계 단계에서 정한다.

## 7. 이번 Feature에서 의도적으로 하지 않을 일 (제안)

- Redis 캐시 또는 대화 기록 저장
- Kafka를 통한 독서 이벤트 처리
- LLM 기반 추천과 Tool Calling
- 소셜 기능, 서재 공유 및 권한 등급
- 복잡한 독서 통계, 리포트 및 데이터 분석

후속 확장 가능성은 고려하되, 해당 기술을 위해 선제적으로 불필요한 구조를 만들지 않는다.
